### 인간의 판단은 소프트웨어 공장을 떠나지 않고 위치를 바꿈 | GeekNews

(https://news.hada.io/topic?id=32737)

- 소프트웨어 공장이 코드 생성을 자동화해도 제품 의도·시스템 설계·품질 기준·최종 배포에는 인간의 판단과 책임이 필요함
- Claude Code나 Codex만으로 충분할 수 있지만, 작업을 이벤트 기반 큐로 반복 처리하고 에이전트 사이에 상태·맥락·증거를 안정적으로 넘겨야 할 때 공장이 유용함
- 테스트가 모두 통과해도 에이전트가 테스트 자체를 바꾸거나 의도와 다르게 구현할 수 있어, 타입 검사·테스트·보안 검사·인간 검토를 위험도에 맞춰 배치해야 함
- 병렬 에이전트 수와 달리 인간의 인지 대역폭은 늘어나지 않으며, 생성된 코드와 결정 이유를 따라가지 못하면 이해 부채와 검토 병목이 커짐
- 좋은 공장은 사람을 제거하지 않고 의도·맥락·취향·위험·장기 소유권이 중요한 지점에 배치하며, 신뢰 변화에 따라 제약과 자율성 수준을 조정함
소프트웨어 공장이 필요한 시점
- 소프트웨어 공장은 소프트웨어 작업을 둘러싼 반복 가능한 실행 루프임
- 일반적인 Claude Code나 Codex, 여러 세션, 검증과 제약을 포함한 명세만으로도 상당한 작업을 처리할 수 있음
- GitHub 이슈 여러 개에 구현 기준과 인간 개입 조건을 붙여 처리할 수도 있지만, 시스템이 반복적이고 이벤트 기반으로 동작해야 할 때 공장이 유용해짐
- 작은 공장 루프는 다음 절차로 구성할 수 있음
 - GitHub 이슈와 저장소 지침을 먼저 읽음
 - 명시된 인수 조건만 구현하고 인증·결제·마이그레이션·기존 테스트 단언은 수정하지 않음
 - 브랜치에서 검토 가능한 크기의 변경을 만듦
 - lint, test, build를 실행하며 필수 검사를 실행할 수 없으면 중단하고 이유를 남김
 - 실행한 검사, 남은 위험, 인간이 결정할 사항을 담은 초안 PR을 만들되 병합하지 않음
- 목표와 검사를 바탕으로 루프를 계속 진행하고, 특정 레이블이 붙은 GitHub 이슈를 폴링하거나 매일 열린 PR을 검토할 수 있음
- 브랜치 보호는 병합 경계를 강제하고, 인간은 준비 상태 판단·검토·최종 병합을 담당할 수 있음
이벤트 기반 작업 큐와 상태 관리
- Slack 트리거, GitHub 이슈, Linear 또는 백로그에서 들어온 작업을 격리된 클라우드 환경에서 분류·구현·테스트하고 명시적인 인간 감독까지 연결해야 할 때 공장을 추가할 수 있음
- 일부 공장은 프로덕션을 감시하는 에이전트가 이슈를 등록하고, 해당 이슈를 다시 분류하는 단계까지 루프에 포함함
- 공장이 특히 유용한 문제는 다음과 같음
 - 서로 다른 실행의 동작을 일관되게 유지함
 - 에이전트 사이에서 작업을 넘김
 - 여러 세션이 같은 이슈를 가져가지 못하게 막음
 - 작업 증거를 보존함
 - 인간 검토가 밀리면 프로덕션 배포를 중단함
- Warp는 들어오는 이슈를 ready-to-implement ,ready-to-spec ,needs-info ,wait-to-implement 의 네 상태로 분류하고, 레이블로 다음 에이전트를 실행함
 - 레이블은 큐와 잠금 역할을 동시에 수행함
 - 세션은 준비 상태로 표시된 작업만 가져가므로, 인간이 영구 거절하지 않고도 작업을 보류할 수 있음
- 일반적인 Claude/Codex 작업과 공장에는 세 가지 주요 상호작용이 있음
 - 조향(steering): 에이전트에 입력을 주고 작업 방향을 수정함
 - 알림: 요구사항의 모호함, 위험한 작업, 인간 입력 필요 등 차단 원인을 전달함
 - 인계(handoff): 작업 상태와 맥락을 다른 에이전트나 인간 검토자에게 넘기며 완료된 일·남은 일·인계 이유를 보존함
- 인간은 마지막 변경분만 승인하지 않으며, 초기 작업을 구체화하고 구현 도중 방향을 바꾸며 인계를 돕거나 프로덕션 배포를 중단할 수 있음
- 직접 인프라를 구축하는 대신 Factory, Warp, HumanLayer 같은 제품을 검토할 수 있음
병렬 개발에서 인간이 맡아야 할 판단
- 간단한 상시 가동 공장에서는 여러 클라우드 작업을 병렬 실행할 수 있으며, 일부는 실제 사용자·인증·결제·구독을 포함한 고객용 프로덕션 애플리케이션일 수 있음
- 오픈소스 프로젝트, 책의 보조 사이트, 도구, 자체 앱, 마이그레이션과 대규모 기능 작업은 서로 영향 범위가 달라 같은 수준의 자율성을 적용할 수 없음
- 속도·생산성·자율성을 높이려면 인간 코드 검토와 입력이 반드시 필요한 위치를 정해야 함
 - 명세와 요구사항
 - 제품 의도와 디자인
 - 완료 여부 검증
 - 기존 시스템의 회귀 여부
 - 품질 기준 충족 여부
- 충분한 맥락이 있으면 에이전트가 구현, 테스트 실행, 실패 분석, 코드 수정을 수행할 수 있어 코드 생성 자체가 가장 큰 걱정거리는 아님
- 인간의 취향을 환경에 충분히 인코딩해야 제한된 주의를 가장 필요한 지점에 집중할 수 있음
- 생성되는 코드 전체를 사람이 읽는 것은 현실적이지 않으며, 모든 작업이 로켓처럼 극단적으로 높은 위험을 갖는 것도 아님
- 인간 판단은 시스템에서 가장 위험한 부분과 주관적 품질이 중요한 프런트엔드·동작 설계에 집중할 수 있으며, 코드 전체에 똑같이 적용할 필요는 없음
인지 대역폭과 잘못된 프로젝트 문제
- 수십·수백·수천 개의 에이전트를 병렬 실행해도 인간의 인지 대역폭은 같은 비율로 확장되지 않으며, 인지 부채와 이해 부채로 이어질 수 있음
- 과거에도 동료의 방해 이후 흐름 상태로 돌아가는 문맥 전환 비용이 문제였지만, 에이전트 작업에서는 하루에 5~10개 프로젝트나 기능 세션을 오갈 수 있음
- 잘 정의되고 검증 방법이 명확한 작업에는 자율성을 높일 수 있지만, 위험이나 미묘한 판단이 있는 작업에는 계속 주의를 기울여야 함
- 모든 결과가 한 사람의 검토로 모인다면, 공장은 남은 결정을 얼마나 싸고 쉽게 만드는지를 기준으로 최적화해야 함
- 여러 프로젝트를 병렬 진행하다 다른 프로젝트 세션에 다크 모드 프롬프트를 입력해 필요 없는 기능을 구현한 사례는 프로젝트 식별 오류도 시스템적으로 막아야 함을 보여줌
- 공장은 소프트웨어 엔지니어링 문화와 팀 문화를 시스템에 인코딩하고, 행동 규칙과 소유권 및 최종 책임자를 명확히 해야 함
모든 검사가 초록색이어도 안전하지 않은 이유
- AI는 테스트를 통과하라는 요청에 테스트 자체를 바꾸거나 조건만 만족하도록 코드 논리를 수정할 수 있으며, 이는 기능 의도와 테스트 의도를 모두 충족했다는 뜻이 아님
- 공장의 결과가 모두 초록색이어도 실제 품질을 보장하지 않으므로, 초기 구축 단계에는 검사와 검증이 의도대로 작동하는지 면밀히 확인해야 함
- GitHub 인증 제공자를 추가하면서 UI 공간이 세 개뿐이라는 이유로 기존 제공자 하나를 제거할 수 있으므로, 보존해야 할 동작과 변경 금지 범위를 명시해야 함
- GitHub 이슈나 Slack 메시지처럼 신뢰할 수 없는 입력을 읽는 공장은 적대적 지시나 공급망 공격에 노출될 수 있음
- Vercel의 소프트웨어 공장은 에이전트를 격리된 샌드박스에서 실행하고 작업에 필요한 비밀만 제공함
 - 실행 하나가 침해돼도 해당 작업에 필요하지 않은 자원에는 접근할 수 없도록 방어 계층을 구성함
다시 살릴 프로젝트를 고르는 판단
- 시간과 우선순위 부족으로 중단했던 주말·개인 프로젝트는 에이전트로 완성하기 쉬워졌지만, 실제로 존재하고 출시될 가치가 있는지는 여전히 사람이 결정해야 함
- 사용자가 5명뿐이어도 출시하면 유지보수와 품질 기준을 책임져야 할 수 있음
- 오래된 GitHub 프로젝트를 되살리는 작업은 단순 완성보다 많은 판단을 요구함
 - 변경된 의존성, 빌드 실패, 오래된 구성 요소와 보안 취약점을 갱신함
 - 업그레이드하거나 현대적 언어·프레임워크로 이전하기 전에 기존 동작을 보존할 테스트를 추가함
 - Twitter Bootstrap 기반 UI를 Tailwind와 shadcn으로 다시 구현할지 판단함
- 에이전트가 작업 속도를 높여도 제품 감각과 취향, 대상 사용자, 시장성, 개인용인지 공개용인지 판단하는 데는 시간이 듦
- 누구나 비슷한 제품을 빠르게 만들 수 있는 상황에서도 출시할 가치가 있는지, 인간의 시간을 어디에 쓸지 명시적으로 결정해야 함
82분 동안 실행한 샘플 공장
- 참고 구현으로 Factory 저장소, 데모 애플리케이션, 워크숍을 제공함
- 데모는 영화 앱에 즐겨찾기, 검색, 다크 테마 같은 기능을 구현하며, 일회성 구현 요청에서는 발견하지 못했을 실제 문제를 검증 단계에서 찾아냄
- 실행 약 60분 시점에도 느리게 진행되는 것처럼 보였지만 검증기들은 계속 동작 중이었음
- 개별 작업은 10~20분으로 예상할 수 있으나 검증·재시도·브라우저 검사·인간 검토를 포함하면 2~4배 오래 걸릴 수 있음
- 추가 시간은 품질과 시스템 신뢰를 높일 수 있으며, 측정 지표로 병합된 PR당 비용과 코드 보존 기간을 이해 부채 지표로 고려할 수 있음
- 모든 지연이 유용한 것은 아니므로 다음 시간을 구분해야 함
 - 검증기가 실제 문제를 발견한 시간
 - 요구된 증거를 생성한 시간
 - 공장 자체의 실행 오버헤드
- 가치 없는 검사를 많이 실행한다고 고품질 공장이 되는 것은 아니며, 반복 검사가 무관하거나 시끄러운지 또는 실제 안전성을 높이는지 평가해야 함
검증 예산 설계
- 검증 비용은 성능 예산과 비슷한 검증 예산으로 관리할 수 있음
- 개발 생명주기 초기에 빠르고 연속적으로 실행할 검사는 다음과 같음
 - 타입 시스템과 타입 검사
 - 자동화 테스트
 - lint와 아키텍처 규칙 검사
- 비용이 크지만 가치가 높은 검사는 초안 PR 전후처럼 뒤쪽에 배치할 수 있음
 - 전체 테스트 모음
 - 변이 테스트
 - 브라우저 테스트
 - 보안 검사
- 실제 테스트를 요약문으로 대체해서는 안 되며, 빠른 반복 루프를 과도하게 늦추지 않는 위치에 검사를 배치해야 함
- 검사 개수가 품질과 같지는 않으므로 신호 대 잡음비를 실험하고, 시스템의 신뢰도에 따라 제약을 의도적으로 강화하거나 완화해야 함
배포되지 않은 실행의 분류와 비용
- Vercel은 각 에이전트 실행을 success ,flawed ,blocked ,manual 로 표시하며success 만 프로덕션에 배포함
 - flawed : 잘못된 구현이나 불충분한 맥락 때문에 수정이 필요함
 - blocked : 환경에 자격 증명 등이 없어 추가 제공이 필요함
 - manual : 공장이 아직 넘어서는 안 되는 인간 판단의 경계임
- flawed 와blocked 에는 기계적인 해결책이 있을 수 있지만,manual 은 신뢰와 권한의 문제임
- 분류만으로는 실행 비용을 알 수 없으므로 단계별 소요 시간을 함께 측정해야 함
 - 거절이 없었던 빠른 검색 기능은 7분이 걸림
 - 두 번의 거절과 중간 인간 결정을 거친 즐겨찾기 기능은 56분이 걸림
- 샘플 공장은 첫 번째 이슈를 중단하고 factory:needs-info 로 옮겼지만, 인간이 답을 어디에 입력해야 하는지 알기 어려웠음
- 수동 실행은 공장이 멈췄을 때가 아니라 사람이 다음 행동을 명확히 알 때 완료됨
위험에 따라 달라지는 자율성
- 에이전트의 자율성은 모든 프로젝트에 적용되는 단일 설정이 아님
- 검증은 신뢰를 높이고 에이전트에 더 많은 자율성을 부여할 근거를 만듦
- 중요 변경이 여러 검사를 통과하고 인간의 직접 확인까지 거쳤다면, 같은 프로젝트의 유사 작업에는 다음번에 더 높은 자율성을 줄 수 있음
- 검증 수준은 위험에 따라 달라져야 하며, 목표는 거대한 체크리스트가 아니라 가장 좋은 신호 대 잡음비임
통과한 기능을 이해하지 못한 경험
- 여러 Claude 세션과 프로젝트를 병렬 진행하던 중 즐겨찾기 기능이 구현됐고 테스트와 브라우저 확인을 통과해 병합됐음
- 며칠 뒤 탭 효과를 수정하려고 코드를 다시 보자, 승인했던 저장소의 기능이 어떻게 동작하는지 설명할 수 없었음
- 저장소 전반은 이해했지만 생성되는 코드의 속도를 인간의 이해가 따라가지 못했고, UI와 효과의 동작을 단계별로 다시 학습하며 기능을 재작업해야 했음
- 테스트 통과와 변경 승인이 구현 이해를 보장하지 않으며, 이해 부채는 이후의 미세 조정과 에이전트 지시에 직접 영향을 줌
병렬 작업이 결정의 맥락을 지우는 방식
- 5~10개 세션을 병렬 실행하면 검토량만 늘어나는 것이 아니라 여러 정신 모델이 작업 중단 동안 식어버림
- 대화 압축, 접근법 거절, 여러 시도와 에이전트 페어링이 누적되면 세션에서 무슨 일이 있었는지 기억하기 어려움
- 대화를 위로 스크롤해도 압축 전 정보가 모두 남지 않으며, 모든 결정을 머릿속에 저장할 수도 없음
- 코드는 어떤 결정이 내려졌는지는 보존하지만 왜 그 결정을 내렸는지는 보존하지 않는 경우가 많음
- 중요한 작업에서는 에이전트가 문제 해결 경로와 배운 점을 기록하게 할 수 있음
 - 저장소에 커밋할 수 있음
 - 로컬에만 보관할 수 있음
 - 팀과 공유할 수 있음
- 이런 기록은 세션 기록이나 인간의 기억에만 의존하지 않고 이후 판단에 활용할 수 있음
소유권은 사라지지 않음
- 인간이 직접 입력하는 코드 비율이 크게 낮아져도 인간의 소유권까지 낮아질 필요는 없음
- 사람은 계속 다음 사항을 결정함
 - 해결할 문제
 - 아키텍처
 - 품질 기준
 - 신뢰할 검증 신호
 - 배포하기에 증거가 충분한 시점
- 시스템이 실패했을 때 “에이전트가 작성했다”는 말은 책임을 대신할 수 없으며, 인간 판단은 루프에서 사라지는 대신 다른 위치로 이동함
- 기계가 더 강하고 빠르며 결정적인 신호를 만들 수 있는 단계에서는 사람을 빼고, 맥락·취향·위험·장기 소유권이 중요한 단계에는 사람을 집중해야 함
- 좋은 공장은 인간 개입을 얼마나 완전히 없앴는지가 아니라 어디에 배치했는지로 평가해야 함
- 의도·시스템 형태·품질 기준은 상류에서 사람이 정하고, 자동화된 역압력이 약하거나 결과가 주관적인 부분은 코드를 직접 검토해야 함
- 결정적인 검증 신호는 가능한 한 이르고 지속적으로 루프에 넣되, 시스템이 신뢰를 얻거나 잃는 정도에 따라 제약을 조정해야 함
- 프로덕션에 배포되는 코드에는 최종적으로 인간 소유자가 필요함
