- AI 코딩 도구는 숙련자가 조정·검토할 때 가장 유용하지만, 초보자가 전문성을 쌓는 데 필요한 시행착오와 마찰을 우회해 차세대 개발자의 성장 경로를 약화할 수 있음
- 강한 AI 지원을 받은 초보자는 계획 단계를 건너뛰고 실력에 대한 착각에 빠진 반면, 제안을 제한적으로 활용하거나 무시한 참가자는 의도한 코드를 더 효과적으로 완성함
- LLM 학습은 학생이 먼저 멘토를 올바르게 이끌어야 하는 역전된 학습 구조이며, 낯선 분야에서는 필요한 질문과 검증 기준을 몰라 모델의 오류에 계속 의존할 수 있음
- UPenn 연구에서 일반 AI를 이용한 학생은 교과서만 쓴 집단보다 시험 성적이 17% 낮았지만, 스스로 문제를 풀도록 유도한 GPT Tutor는 연습 성과를 127% 높여 생성과 교육 중심 사용의 차이를 보여줌
- 전문성을 키우려면 AI를 코드 생성기보다 대화형 문서·동적 튜토리얼·소크라테스식 연습 도구로 쓰고, 인지 부채와 기계적 작업의 인지적 외주화를 구분하며 공식 문서·동료·직접 실험으로 결과를 검증해야 함
숙련된 조정자 역설
- AI 에이전트를 효과적이고 책임감 있게 관리하는 능력은 에이전트를 계속 사용하면서 약화될 수 있는 능력과 같음
- 현재 AI 모델에서 가장 큰 이익을 얻는 사람은 대체로 AI 도구 이전부터 수년 또는 수십 년 동안 현장에서 일하며 지식을 굳힌 숙련 개발자임
- LLM 등장 무렵 업계에 들어온 개발자는 충분한 경험을 쌓기 전에 AI 코딩 도구로 속도를 높이라는 권고나 의무를 받음
 - 도구를 제대로 사용하려면 이미 축적된 전문성이 필요함
 - 초보자가 업계의 속도를 따라가기 위해 전문가 수준의 능력을 요구받는 모순이 생김
전문가처럼 행동해야 하는 초보자
- 업계에서는 AI를 쓰지 않으면 뒤처진다는 메시지와 함께, 최상의 결과를 내려면 높은 수준의 사고가 필요하다는 요구가 동시에 이어짐
- 단순한 “vibe coding” 대신 견고한 명세, 적절한 설계 패턴, 세심한 결과 검토가 필요하며 이해하지 못한 코드는 배포하지 말아야 함
- 이런 판단 능력과 좋은 감각은 오랜 시간 마찰과 난관을 겪으며 형성됨
- AI 도구가 전문성을 요구하면서도 전문성을 만드는 마찰을 우회한다면, 사용자가 도구를 효과적으로 다룰 전문가로 성장할 경로가 불분명해짐
이해 없는 자신감
- AI가 개인 교사처럼 학습을 가속하고 구문이나 모호한 부분을 대신 처리해 줄 것이라는 기대와 달리, 깊은 작동 원리는 계속 추상화될 수 있음
- JetBrains가 인용한 연구 The Widening Gap: The Benefits and Harms of Generative AI for Novice Programmers는 AI 지원 수준을 달리한 실시간 코딩 세션에서 초보자의 행동과 학습을 분석함
- AI 지원에 크게 의존한 참가자는 Copilot이 대신 추론한다는 이유로 중요한 계획 단계를 자주 생략했고, 실제 이해 대신 “실력에 대한 착각”을 얻음
- AI 사용을 제한한 참가자는 잘못되거나 도움이 되지 않는 제안을 무시하는 부정적 전문성(negative expertise) 을 발휘함
 - AI에 끌려가기보다 자신의 해법 작성에 집중함
 - 이미 만들려고 했던 코드를 빠르게 구현하는 용도로 AI를 사용함
- AI를 가장 자유롭고 자신 있게 사용한 초보자는 문제 해결의 핵심 단계를 생략한 뒤 길을 잃은 반면, 가장 좋은 성과를 낸 초보자는 AI 지원을 크게 줄이거나 무시함
학생이 멘토를 이끄는 역전된 학습
- LLM은 경험이 많을수록 조정·감사·검증이 가능해 더 큰 이익을 주지만, 지식이 적을수록 사용자를 잘못된 방향으로 이끌 수 있음
- 역전된 학습에서는 학생이 먼저 멘토인 LLM을 안내하고, 답변을 받은 뒤 다시 방향을 조정해야 함
- 프롬프트 형태에 민감하고 사용자의 관점에 맞춰주는 LLM은 낯선 영역에서 자신이 실제보다 많이 안다고 믿게 만들 수 있음
 - 사용자는 무엇을 모르는지 알지 못해 최선의 답을 끌어낼 질문 자체를 찾기 어려움
 - LLM은 사용자가 북쪽이라고 제안한 곳을 언제나 북쪽으로 가리키는 나침반처럼 작동할 수 있음
- 앞선 연구에서는 기초 계획과 습관이 좋았던 참가자도 Copilot의 빠른 코드 생성에 끌려 계획 단계를 생략했고, 결국 LLM이 만든 오류를 LLM으로 수정해야 했음
- AI 모델에는 판단력·공감·교육적 의도가 없으며, 답은 경험이 아니라 훈련 데이터의 패턴 보간에 기반함
- 끝없이 답을 제공하는 도구는 중독성을 띨 수 있고, 생성된 해법에 깊이 들어갈수록 마무리도 AI에 의존하게 됨
 - 이 과정은 정신 모형을 만드는 데 필요한 문제 해결의 마찰을 우회함
 - 숙련 개발자도 같은 현상을 겪을 수 있음
마찰이 개발자 직관을 만드는 과정
- 숙련은 관찰과 대화만으로 생기지 않으며 경험, 반복, 시행착오와 실패가 필요함
- 요리를 계속 관찰하고 질문하면 미디엄 레어 스테이크를 설명할 수는 있어도, 처음 직접 조리할 때는 지나치게 익힐 가능성이 큼
- 개발자는 로그가 없는 모호한 오류 추적, 구현 방식에 따른 미세한 성능 차이, 확장되지 않는 접근법의 재작성 등을 직접 겪음
- 이런 적용된 마찰이 문제가 생길 코드를 직감하는 개발자 감각을 형성함
 - 독일어 Fingerspitzengefühl은 이를 “손끝의 감각”으로 나타냄
 - 문제 해결의 기계적 과정을 피하면 이런 근육 기억이 만들어지지 않음
생성 도구와 교육 도구의 차이
- UPenn의 2025년 대규모 연구 Generative AI without guardrails can harm learning은 수학을 배우는 학생 1,000명을 추적함
 - 일반 LLM을 지팡이처럼 사용한 학생은 교과서만 사용한 학생보다 17% 낮은 성적을 냄
 - AI 지원 집단은 자신의 학습이 잘되고 있다고 생각함
- LLM을 답 생성기가 아니라 소크라테스식 토론 상대로 사용하면 성찰적·비판적·독립적 사고를 자극할 수 있다는 연구도 있음
- UPenn 연구의 “Tutor” 버전은 학생이 도움을 요청한 뒤 문제를 독립적으로 풀게 함
 - GPT Tutor 집단은 AI 지원 연습 세션에서 127% 높은 성과를 냄
 - 실제 시험에서는 교과서 집단과 비슷한 점수를 받음
- Tutor 방식은 AI를 생산 수단으로 쓰지 않고 인지 작업을 학습자에게 돌려주며, 마찰을 유지해 전문성으로 이어지는 흔적을 남김
- Anthropic의 2026년 연구 How AI assistance impacts the formation of coding skills는 의도적인 능력 개발, 인지적 노력, 고통스럽게 막히는 경험이 숙련 형성에 중요하다고 봄
- AI 코딩 도구를 통한 가장 생산적인 학습은 코드를 거의 생성하지 않을 때 일어날 수 있음
전문성 공급망의 붕괴 가능성
- LLM이 코드 작성·디버깅·시스템 설계를 모두 맡을 수 있다는 전제에서는 프로그래밍 지식이 더는 중요하지 않고 자연어만으로 개발할 수 있다는 전망이 나옴
- 이 전망은 LLM이 새로운 세대의 개발자가 되어 사람의 지식 공백과 모델이 만든 복잡성까지 처리할 것이라는 대규모 투자 가정에 기대고 있음
- 소프트웨어 개발은 논리, 수학, 문제 해결, 비판적 사고, 계획, 소통, 창의성이 만나는 작업이며 패턴 탐지만으로 모두 해결되지 않음
- Sentry 공동 창업자 David Cramer는 LLM이 쌓인 문제를 나중에 스스로 고쳐줄 것이라는 기대를 “과학 실험”으로 보고, 대량 병렬 생성 코드의 결함을 지적함
- 전문성 공급망이 붕괴할지 변화할지는 AI를 교육 중심으로 전환할 수 있는지에 달려 있음
- 깊은 이해보다 코드 생성을 우선하면 오늘 생성되는 코드를 물려받을 차세대 전문가가 성장하지 못함
Friction First 학습법
- Joel Spolsky가 2002년에 정리한 누수되는 추상화의 법칙에 따르면 코드 생성 도구를 포함한 추상화는 누수되며, 이를 제대로 처리하려면 내부 작동을 배워야 함
 - 추상화는 작업 시간을 줄여도 학습 시간을 없애지는 않음
- 기초를 배우려는 개발자는 Java에서 Spring Boot, JavaScript에서 React, CSS에서 Tailwind부터 시작하지 않는 편이 좋으며, LLM은 궁극의 누수되는 추상화로 볼 수 있음
- 프로그래밍 전문가가 되려면 순수 코드 생성 기능은 대체로 배제하고 다음 용도로 활용해야 함

대화형 문서와 학습 도구
 - 동적 튜토리얼 생성
 - 소크라테스식 연습
 - AI 교사도 환각 위험이 있어 유일한 학습 자료로 의존할 수 없음
 - 생성 코드를 감사할 능력이 없다면 생성된 개념의 정확성도 감사하기 어려움
 - 공식 문서, 인간 동료, 직접적인 시행착오로 결과를 검증해야 함
 - Kent Beck은 코딩을 많이 할수록 작업하는 도메인을 더 깊이 이해할 수 있다고 봄
 - 느리고 신중한 경로가 전문성 성장에 적합하지만, 기업의 AI 사용 의무화와 개발 도구·IDE의 AI 통합은 이를 어렵게 함
 - 일부 도구는 주로 숙련 엔지니어를 겨냥하며, Cursor는 사용자가 직접 찾지 않으면 코드 보기를 감춰두기도 함
 - 일부 기업은 경력 수준과 무관하게 모든 코딩 작업을 AI로만 수행하도록 강제함

AI 지원을 쓰기 전 확인할 질문
- AI 없이도 이 작업을 완수할 수 있는가
- 모델을 이해 심화에 쓰는가, 답을 빨리 얻는 데 쓰는가
- 생성 결과를 감사·검증해야 할 때 무엇이 일어나는지 충분히 설명할 수 있는가
- 새로운 개념을 배울 때 올바른 질문을 알 수 있을 만큼 사전 조사를 했는가
- 공식 문서, 일반 검색, StackOverflow, Reddit 등 다른 방법으로 접근법을 교차 검증했는가
- 100번 반복된 단순 작업인가, 아니면 과정에서 고차원적 의사결정이 필요한 작업인가
- 경험 많은 개발자에게도 이런 질문은 특히 새로운 분야를 배울 때 계속 필요함
인지 부채와 인지적 외주화
- 인지 부채(cognitive debt) 는 자신의 판단과 결정을 포기하는 것이고, 인지적 외주화(cognitive offloading)는 기계적이거나 지루한 작업을 위임하는 것임
- 고통스럽게 막히는 경험은 학습에 도움이 되며, 답 생성으로 돌아가지 않으려면 규율과 노력이 필요함
- LLM이 인간 학습의 기본 원리를 바꾸지는 않았지만 새로운 학습 방법은 제공함
지능은 계량 판매되는 상품이 아님
- 능력은 능동적인 참여 없이 발전하지 않으며, 전문성에는 직접적이고 지속적인 참여와 필수적인 마찰이 필요함
- 코드 줄 수와 소비 토큰에만 집중해 전문성 공급망이 마르면, 지능을 전기나 수도처럼 계량 판매한다는 Sam Altman의 전망이 현실이 될 수 있음
- 도메인 지식이 희귀해지고 개발자가 AI 구독 없이는 작업을 시작하기 어려운 상태에 빠질 수 있음
- ARC-AGI Benchmark를 만든 François Chollet에 따르면 LLM은 정적인 능력 데이터베이스이자 보간 엔진이지만, 소프트웨어 엔지니어링은 적응과 새로운 문제 해결의 작업임
- 완전히 새로운 시스템 장애는 기존 패턴의 보간만으로 해결할 수 없음
