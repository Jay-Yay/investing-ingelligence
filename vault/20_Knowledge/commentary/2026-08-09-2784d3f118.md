## 첨부 기사 원문
### “코드는 결코 어려운 부분이 아니었다”는 말은 모든 프로그래머에 대한 모욕이다 | GeekNews

(https://news.hada.io/topic?id=32276)

- AI가 프로그래밍을 바꾸고 있지만 코딩을 쉬운 작업으로 치부하면, 오랫동안 요구된 기술·경험·노력과 소프트웨어가 여전히 버그투성이라는 현실을 무시하게 됨
- 무엇을 만들지 결정하고 고객을 이해하는 일도 중요하지만 구현보다 본질적으로 어렵다고 단정할 수 없으며, 개발자마다 고객 중심 역할과 기술적 장인정신을 중시하는 정도가 다름
- 성공적인 소프트웨어에는 사용자와 사업에 대한 이해뿐 아니라 시스템을 제대로 구현하는 코드 품질과 전문성도 필요하므로, 어느 한쪽만 중요하다는 극단론을 피해야 함
- 복잡성·유지보수·고객과 사용자 사이의 긴장은 계속되는 반면 도구와 언어, 개발자의 역할은 바뀌므로 과대광고와 실효성을 구분하며 인접 분야까지 학습할 필요가 있음
- 경력자는 사용자 경험과 사업을, 초급자는 포인터·메모리·네트워크·자료구조 같은 기초를 넓혀야 하며, 누구도 자신의 이해·판단·공감·취향과 책임을 AI에 넘겨서는 안 됨
코딩이 쉽다는 말이 놓치는 현실
- 프로그래머는 AI와 제로금리정책(ZIRP) 이전부터 높은 수요와 급여를 누렸지만, 동시에 스트레스·과로·번아웃을 겪어 왔음
 - 기업은 이른바 10x ninja rockstar 개발자를 찾으며 LeetCode 면접으로 지원자를 평가해 왔음
 - 코딩이 정말 쉽다면 대학을 갓 졸업한 주니어만으로도 충분해야 하지만, 실제 채용 관행은 그렇지 않았음
- 소프트웨어 개발에는 오랫동안 축적된 지식과 훈련이 필요함
 - Clean Code, The Pragmatic Programmer, The Art of Computer Programming, SICP처럼 방대한 전문 서적이 존재함
 - 부트캠프와 대학 학위 과정 전체가 프로그래밍 교육에 투입됨
- John Carmack과 Fabrice Bellard 같은 개발자가 뛰어난 인물로 평가받는다는 사실도 코딩 역량의 차이를 보여줌
- 사람들이 코드 복제에 분노하는 이유는 코드에 시간과 노력, 정체성을 쏟았기 때문임
 - AI로 인해 직업적 목적과 정체성을 잃는다고 느끼는 현상 역시 코딩이 사소한 작업이라는 평가와 충돌함
- 코딩이 쉽다는 전제로는 소프트웨어가 여전히 심각한 버그를 품는 현실도 설명하기 어려움
무엇을 만들지 결정하는 일도 자동으로 더 어렵지는 않음
- 제품 결정을 가장 어려운 업무로 본다면 제품 관리자에게도 개발자 수준의 엄격한 다단계 면접과 더 높은 보상이 적용돼야 하지만 현실은 그렇지 않음
- 고객 이해가 구현보다 어렵다면 시장 조사자, 사용성 전문가, 고객 성공 담당자, 비즈니스 분석가도 소프트웨어 회사의 핵심 인재로 대우받아야 함
- 영업 담당자가 계약을 위해 고객에게 새 기능을 약속하면 개발자는 흔히 반발함
 - 그러나 구현은 쉽고 수요 발견은 어렵다는 논리대로라면, 이는 돈을 낼 고객의 실제 수요를 찾아낸 사례가 됨
- 코딩이 쉬운 작업이라면 제품 변형을 열 가지씩 만들어 시장에서 성공하는 버전을 확인할 수도 있겠지만, 실제로는 그렇게 간단하지 않음
하나의 전형적인 프로그래머는 없음
- 소프트웨어 개발의 대부분은 이해관계자와 대화하고 고객 요구와 우선순위를 파악하는 일이라는 통념이 있음
- 실제로 많은 프로그래머는 이해관계자나 고객과 대화하기를 원하지 않으며, 프리랜서와 창업자, 특히 소프트웨어 개발사 창업자가 주요 예외임
 - 이들이 바라는 우선순위의 명확성이란 흔히 무엇을 해야 하는지 알려주고 이틀마다 바꾸지 말라는 요구에 가까움
- “코드를 쓰는 것이 아니라 고객 문제를 해결한다”고 말하는 개발자도 모나드, 메모리 안전성, DRY 원칙에는 적극적으로 의견을 냄
 - 반면 고객 이해는 가상의 사용자 페르소나에 머물고, 사용성 개념인 어포던스(affordance)조차 제대로 이해하지 못할 수 있음
- 다른 개발자들은 소프트웨어 개발을 이론 구축으로 보고 프로그램을 수학적 증명으로 이해하며, 모든 커밋이 하나의 이야기를 전달해야 한다고 봄
 - 이들에게 PHP 파일을 FTP로 올려 고객 문제를 해결하는 방식은 용납하기 어려운 잘못이 됨
- 소프트웨어 장인정신과 고객 공감을 모두 깊이 중시하는 개발자도 있지만, 모든 프로그래머를 하나의 평균적 유형으로 일반화할 수는 없음
고객 이해와 좋은 코드는 모두 중요함
- 사용자와 대화하고 경험을 이해하며 공감하는 일, 고객 문제를 해결하고 이해관계자의 방향을 일치시키는 일은 소프트웨어 프로젝트 성공에 필수적임
- 좋은 코드를 만드는 일 역시 기술과 인내, 세부 사항에 대한 주의, 경험과 지혜가 필요한 장인 작업이며 앞으로도 중요함
- 구축하는 시스템을 깊이 이해하는 동시에 그것을 왜 구축하는지도 깊이 이해해야 함
- “코드는 쉽다”거나 반대로 “코드는 자동화할 수 없는 인간의 예술적 표현이다”라고 선언하는 양극단으로는 변화에 대응하기 어려움
- 적응이 곧 LLM 유행에 올라타거나 AI 에이전트 무리를 관리하는 사람이 되라는 뜻은 아님
 - AI 생성 코드를 도둑질한 저품질 결과로 규정하고 거품 붕괴만 기다리며 전면적으로 싸우라는 뜻도 아님
- 업계 전반의 지각변동을 인정하고 무엇이 바뀔 가능성이 있으며 무엇이 변하지 않는지 파악해야 함
변하지 않는 조건
- 소프트웨어는 계속 복잡해지고 언제나 유지보수가 필요함
 - 비트 부패(bit-rot)와 엔트로피는 피할 수 없으며 하드웨어와 소프트웨어 기술도 계속 발전함
 - 추상화의 탑은 갈수록 더 높아짐
- 사용자는 계속 더 많은 것을 원하면서도 더 적은 비용을 지불하려 할 것임
 - 자신의 요구를 정확히 전달하지 못하고, 무엇을 원하는지 스스로도 명확히 알지 못하는 문제도 이어짐
- 비용을 내는 고객과 실제로 사용하는 사용자 사이의 단절, 사업 요구와 고객 요구 사이의 긴장도 남아 있음
- 과장된 기술을 판매하는 사람은 사라지지 않으며 유행 기술은 계속 등장했다가 퇴장함
 - 새로운 VR 르네상스처럼 오래 기다려도 실현되지 않는 유행도 있음
계속 바뀌는 기술과 역량
- 프로그래머는 처음부터 자신의 산업을 스스로 파괴하고 재편해 왔음
 - 천공카드는 더 이상 사용되지 않고, 어셈블리어나 COBOL로 코딩해야 하는 사람도 매우 적음
 - C와 C++의 메모리 버그를 해결하며 쌓은 경험은 Rust, Go, Python, JavaScript 시대에 가치를 잃을 수 있음
- valgrind와 PHP4 시대의 mysql_real_escape_string() 같은 도구와 API도 더는 쓸 필요가 없는 지식이 됨
- dBase, Clipper, HyperCard, Access 같은 기술은 상점과 카페의 오래된 맞춤형 업무 시스템에서 여전히 발견되기도 함
 - 낡은 미들타워가 백업도 불분명한 상태로 이런 시스템을 계속 실행하는 사례가 있음
변화 속에서 성장하는 방법
- 변화가 일어난다는 사실을 받아들이고 새로운 기술에 호기심과 비판적 태도를 함께 유지해야 함
- 과대광고와 실제로 작동하는 기술을 구분하고, 작동한다면 어느 범위까지 유효한지도 판단해야 함
 - 평가 기준이 계속 이동할 수 있으므로 지난 1년 또는 5년을 돌아보며 기술적·경제적·사회적 변화의 속도를 확인해야 함
- 개발자의 역할과 책임은 바뀌므로 자신의 업무와 인접한 분야나 역할을 이해하는 데 시간과 에너지를 투자할 필요가 있음
- 
시니어 개발자
 - 기존 전문성을 더 깊게 쌓는 데만 안주하지 말고 사용자 경험, 고객 인터뷰, 해당 산업 기업의 사업 전략을 학습해야 함
 - 직접 그 업무를 맡지 않더라도 소프트웨어가 사용자에게 전달되기까지 필요한 전체 작업을 더 잘 이해할 수 있음
- 
주니어와 입문자
 - 소프트웨어가 실제로 작동하는 원리를 깊이 학습해야 함
 - JavaScript 개발자라도 포인터, 재귀, 메모리 계층을 이해하면 도움이 됨
 - WordPress 플러그인을 만들더라도 네트워크 프로토콜과 HTTP 작동 방식을 아는 것이 유용함
 - 당장 필요하지 않더라도 LeetCode 문제를 풀고 알고리듬과 자료구조를 학습해야 함
 - “왜 그런가”와 “정확히 어떻게 작동하는가”를 묻는 일을 두려워하지 않아야 함

- 누구든 자신의 이해·판단·공감·취향을 AI에 아웃소싱해서는 안 됨
- AI가 코드를 작성했더라도 자신의 책임을 포기하지 말아야 함
