### “기술 부채”가 아니라 그저 “엉망인 상태”다 | GeekNews

(https://news.hada.io/topic?id=32498)

- 개발팀이 기술 부채라고 부르는 문제 대부분은 미래 비용을 알고 선택한 부채가 아니라, 미숙한 작업·취향 차이·예상하지 못한 복잡성이 뒤섞인 엉망인 상태에 가까움
- 금융 부채는 계약 시점에 규모·비용·조건을 알 수 있지만 기술적 결정의 비용은 대개 나중에 드러나므로, 부채 은유가 전제하는 비용 예측 가능성과 맞지 않음
- 성능을 나중에 개선할 계획으로 단순한 SQL 구조를 택하는 선택은 부채일 수 있지만, 느리고 불안정한 테스트처럼 개발 속도조차 높이지 못하는 문제는 기술 부족이나 부주의에 해당함
- AWS Lambda 기반 이벤트 주도 시스템처럼 확장성을 기대한 선택이 추적과 계측의 어려움으로 돌아오는 경우는, 비용을 알고 진 빚이 아니라 경험의 경계에서 발생한 예상 밖의 결과임
- 소프트웨어를 집이나 작업 공간처럼 지속적으로 청소·정리·재구성해야 하는 대상으로 보면, 문제를 무책임한 차입으로 오해하지 않고 현재 필요한 유지보수로 다룰 수 있음
“기술 부채”가 만드는 잘못된 인상
- 개발자끼리는 기술 부채라는 표현을 쓰더라도, 비개발 직군과 대화할 때는 피하는 편이 나음
- 실제로는 미래 비용을 감수한 의도적 선택보다 단순한 엉망인 상태(mess) 를 가리키는 경우가 많음
- 비개발자는 이를 개발자가 일을 제대로 하지 못했거나 이전 팀의 방식을 마음에 들어 하지 않을 때 쓰는 말로 받아들일 수 있음
- 미리 알지 못했던 문제까지 기술 부채라고 부르면, 조건을 읽지 않고 빚을 낸 사람처럼 보여 진지하지 않은 인상을 줌
- 이전에 소개한 기술 부채를 다루는 방법에서도 이 은유에 관한 긴 문제 제기를 도입부에서 덜어내야 했음
금융 부채와 기술적 결정의 차이
- 기업에는 적정한 부채 규모가 있으며, 그 수준이 반드시 0일 필요는 없음
  - 부채가 너무 적으면 더 비싼 자본인 지분에 지나치게 의존할 수 있음
  - 충분히 차입하지 않으면 가능한 만큼 빠르게 성장하지 못하고, 현재 활용할 수 없는 미래에 돈을 남겨두게 됨
- 금융 부채는 차입할 때 금액과 비용을 정확히 알며, 모든 조건이 문서에 담김
- 실수로 금융 부채를 떠안거나 처음 접한 종류라는 이유로 비용이 갑자기 예상보다 커지는 일은 없음
- 따라서 기술 부채라는 표현이 성립하려면 결정 당시부터 비용과 상환 작업을 이해하고 있어야 함
실제 부채에 가까운 의도적 선택
- StoryTime의 초기 SQL 쿼리는 성능보다 코드 가독성을 우선해, 대체로 쿼리 하나를 assign 하나에 대응하도록 구성함
- 쿼리와 사용자가 늘어나면 페이지 로딩 성능을 높이기 위해 작업을 합치고 개별 데이터베이스 호출 수를 줄여야 한다는 점을 처음부터 알고 있었음
- 미래의 최적화 작업을 감수하고 초기 개발을 쉽게 만든 이 선택은 미래로부터 대출받은 사례에 가까움
- 다만 해당 프레임워크로 많은 SQL을 처리한 첫 프로젝트였으므로, 이런 구성 역시 경험 부족의 결과일 수 있음
  - 같은 유형의 애플리케이션을 두세 번째로 만든다면 처음부터 페이지에 필요한 데이터를 단일 쿼리로 가져올 수 있음
개발 속도를 높이지 못한다면 부채가 아님
- 기술 부채라고 불리는 문제 대부분은 개발을 빠르게 하지 않으며, 일부는 단순히 부주의하거나 미숙한 작업임
- 느리고 불안정하거나 충분하지 않은 테스트가 대표적임
  - 테스트 작성에 능숙하다면 테스트된 코드를 만드는 일이 테스트 없는 코드를 만드는 것보다 더 어렵지 않음
  - 테스트가 프로젝트 속도에 주는 이점은 즉시 누적됨
- 빠르고 신뢰할 수 있는 테스트는 기술과 숙련도에 달려 있음
  - 관련 기법을 알면 빠르고 신뢰할 수 있는 테스트를 쉽게 작성할 수 있음
  - 어떤 방법을 모르는 상태 자체는 부채가 아님
취향과 상충관계를 부채로 부르는 문제
- 어떤 팀은 늘어난 컨테이너 이미지를 기술 부채로 판단해 몇 주에 걸쳐 하나의 이미지로 통합함
- 1년 뒤 팀 구성이 바뀌자 모든 용도를 단일 이미지로 처리하는 상태를 다시 부채로 보고, 여러 목적별 이미지로 분리함
- 소프트웨어 분야에서는 미적 판단이 과소평가되며, 두 선택 모두 반드시 잘못됐다고 볼 수 없음
- 작업이 특정 방식으로 구성돼 있고 그 상충관계가 마음에 들지 않는다는 이유만으로 부채라고 부를 수는 없음
예측할 수 없었던 기술적 비용
- 부채 은유의 가장 큰 문제는 결정 당시 비용을 이해할 수 있다는 예측 가능성을 전제한다는 데 있음
- 기술적 결정이 이런 조건을 충족하는 경우는 매우 드물며, 기술 부채라고 불리는 문제 대부분은 최초 선택 시점에 충분히 이해되지 않았음
- 당시에는 사소한 효율 개선이나 올바른 방식처럼 보였지만, 나중에 그 선택이 폭발적인 특성을 지녔다는 사실을 발견하는 경우가 많음
AWS Lambda 이벤트 주도 시스템 사례
- AWS Lambda 기반 이벤트 주도 시스템을 구축한 팀들은 모놀리식 요청 주도 아키텍처의 확장 문제를 경험한 뒤, 이벤트 방식이 더 잘 확장될 것으로 판단해 전면 도입함
- 문제가 드러났을 때는 시스템의 작동 방식을 이해하는 사람이 없는 경우가 많음
  - 특정 고객 행동에서 장애가 발생한 시스템 구성 요소까지 추적하기 어려움
  - 팀에 같은 시스템을 구축해 본 경험이 없어 필요한 계측 방법도 알지 못했음
- 해당 시스템은 초당 약 0.5개 이벤트만 처리하면서도 이런 복잡성을 안고 있었음
- 이는 기술 부채라기보다 금융 자문가의 추천으로 사모 신용(private credit)을 샀다가 30년 동안 자금을 회수할 수 없다는 사실을 뒤늦게 깨닫는 상황에 가까움
경험의 경계에서 이뤄지는 개발
- 소프트웨어 개발자가 결정할 때마다 모든 비용을 알 수 있다면 이상적이지만, 업계는 그렇게 구성돼 있지 않음
- 개발자는 대체로 자신의 경험 경계에서 작업하므로 결과에 놀라는 일이 자연스러움
- 미리 알지 못했던 문제를 기술 부채라고 부르면, 불확실한 탐색의 결과가 조건도 확인하지 않은 무책임한 차입처럼 보임
집과 작업 공간으로 보는 소프트웨어
- 더 적합한 표현은 엉망인 상태이며, 소프트웨어 프로젝트는 집이나 작업 공간처럼 지속적인 관리가 필요한 대상으로 볼 수 있음
- 프로젝트를 진행하는 동안 일정한 수준의 청소·정돈·재구성이 계속 필요함
  - 도구를 기능별로 정리했다가 실제로는 크기별 정리가 더 편하다는 사실을 깨달을 수 있음
  - 더 이상 도움이 되지 않는 것을 버리지 못하면 잡동사니를 관리하기 어려워짐
  - 이전 소유자에게 넘겨받은 집은 많은 수리가 필요하더라도, 수리하는 동안 계속 그 안에서 살아야 함
- 소프트웨어의 혼란은 예측 가능한 금융 계약보다 변화하는 작업 공간을 유지하고 정리하는 문제에 가까움

- 이 컬렉터는 공개 웹 미리보기(t.me/s/{channel})만 수집하며, 비공개 채널 수집은 이 단계에서 구현하지 않는다.
