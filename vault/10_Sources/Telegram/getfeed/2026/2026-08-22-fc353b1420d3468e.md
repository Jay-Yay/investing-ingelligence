## 첨부 기사 원문

### SSL에 대해 배운 모든 것이 더는 유효하지 않음 [유튜브] | GeekNews

(https://news.hada.io/topic?id=32756)

- 장기 인증서와 수동 갱신에 의존하던 운영 방식은 TLS 1.3, 단기 인증서와 ACME 자동화를 중심으로 바뀌었으며 기존 SSL 관행 대부분은 더는 안전하거나 지속 가능하지 않음
- CA의 부실한 감사와 인증서 오발급, SHA-1 충돌, Heartbleed, 불완전한 폐기 체계가 잇달아 드러나면서 브라우저 업체들이 CA/Browser Forum의 합의 대신 자체 신뢰 정책을 적용하기 시작함
- 완전 순방향 비밀성(Perfect Forward Secrecy)은 인증과 암호화에 같은 장기 개인 키를 쓰던 문제를 해결하고, 세션마다 Diffie-Hellman 일회성 키를 생성해 개인 키가 유출돼도 과거 통신을 복호화할 수 없게 함
- 인증서 최대 유효기간은 2026년 200일, 2027년 100일, 2029년 47일로 줄어들 예정이며, 인증서 50개를 관리한다면 연간 약 500회의 갱신을 처리해야 함
- 발급 자동화만으로는 부족하며 검색, 발급, 배포, 형식 변환, 서비스 재적용, 소유권과 모니터링을 아우르는 인증서 수명주기 관리가 필요하고, 이 기반은 향후 포스트양자 암호 전환에도 중요함
SSL에서 TLS로 바뀐 초기 구조
- 전통적인 SSL 핸드셰이크에서는 브라우저가 지원 버전과 암호 스위트를 보내고, 서버가 하나를 선택한 뒤 신원을 증명하는 인증서를 반환함
  - 브라우저는 인증서의 공개 키를 이용해 premaster secret을 만들어 서버로 전송함
  - 이후 통신은 이 공유 비밀을 기반으로 암호화됨
- 인증서에는 주체와 발급자, 유효기간, 서명 알고리듬, 공개 키 인코딩 정보가 포함됨
- 브라우저는 서버 인증서에서 중간 CA와 루트 CA로 이어지는 인증서 체인을 확인함
  - 루트 인증서는 사용자가 선택하는 것이 아니라 브라우저에 번들로 포함됨
  - 체인이 유효하면 연결을 신뢰하고, 그렇지 않으면 보안 경고를 표시함
- SSL 3.0은 1999년 TLS 1.0으로 바뀌었지만 SSL이라는 명칭은 계속 널리 사용됨
  - TLS 1.1은 2006년 초기화 관련 버그를 수정함
  - TLS 1.2는 2008년 현대적인 암호 스위트를 추가했지만 초기에는 업그레이드가 느렸음
오래된 CSR 관행과 RSA의 혼란
- 과거 널리 복사되던 OpenSSL CSR 명령은 RSA 2048, SHA-1, 3년 유효기간을 사용하지만 현재 기준에는 맞지 않음
  - 새 키를 요청하는 부분은 유효하지만 RSA 2048과 SHA-1, 3년 인증서는 더 이상 권장되거나 허용되는 선택이 아님
- RSA라는 표현은 서로 다른 대상을 가리킬 수 있음
  - 현재 안전하지 않은 RSA 키 교환
  - 타원 곡선 키로 대체되고 있는 RSA 인증서 키
  - 경우에 따라 아직 사용할 수 있는 RSA 서명 알고리듬
  - RSA Conference와 RSA라는 회사
- 같은 약어가 여러 맥락에 쓰이므로 단순히 “RSA를 사용한다”는 말만으로는 어떤 구성을 뜻하는지 알 수 없음
인증서 등급과 CA의 기존 사업 구조
- 인증서 검증은 세 단계로 판매돼 왔음
  - DV(Domain Validation) 는 특정 도메인을 제어한다는 사실만 확인하며 재판매업체 기준 연간 약 200달러였음
  - OV(Organization Validation)는 전화 확인과 기업 존재 여부 조회 등을 추가하며 약 500달러였음
  - EV(Extended Validation)는 추가 서류 절차를 요구하고 약 1,200달러였으며 과거에는 주소 표시줄에 회사명을 표시했음
- Chrome, Safari, Firefox는 2019년 EV의 녹색 표시를 제거함
  - 사용자가 결제 전에 회사 정보를 확인하지 않고 녹색 표시만 신뢰한다는 Google 연구가 근거였음
  - 이후 DV, OV, EV 사이에 사용자가 보는 시각적 차이가 사라짐
- CA가 브라우저의 루트 저장소에 들어가려면 매년 WebTrust 감사를 받아야 했음
  - CA가 감사인을 직접 선정하고 비용을 지급한 뒤 다음 해 재계약 여부도 결정하는 구조였음
  - 감사 시점에만 기준을 충족한 것처럼 보일 수 있다는 이해상충이 존재함
CA/Browser Forum과 합의 구조
- CA들은 2005년 브라우저 업체들과 CA/Browser Forum을 구성하고 Baseline Requirements라는 공통 규칙을 만들었음
- 초기에는 규칙을 바꾸려면 CA와 브라우저의 합의가 필요했으므로 CA가 브라우저의 변경 요구를 막을 수 있었음
- 각 브라우저에도 별도의 루트 프로그램이 있었지만 당시에는 WebTrust 감사와 공통 요구사항 준수가 핵심 조건이었음
- 1999년식 운영 모델에서는 사용자가 CA에 비용을 내고 도메인 제어권을 확인받아 수년간 유효한 인증서를 받았으며, 인증서가 노출되거나 분실되면 새 인증서를 구매해야 했음
CA 침해와 감사 체계의 실패
- 2011년 네덜란드 CA DigiNotar가 침해돼 공격자가 웹 서버에서 CA 루트 저장소로 이동하고 google.com용 비정상 인증서를 발급함
  - 해당 인증서는 이란에서 사용됐으며 이란 정부의 행동일 가능성이 있었지만 입증되지는 않았음
  - 조사 과정에서 패치되지 않은 소프트웨어, 네트워크 분리 부재, 인터넷에 노출된 내부 서비스, 기본 비밀번호가 발견됨
  - 이런 상태에서도 DigiNotar는 감사를 통과했으며, 신뢰가 제거된 뒤 수개월 만에 파산함
- Comodo와 TurkTrust에서도 유사한 인증서 문제가 발생해 기존 CA 신뢰 모델이 흔들림
- 2017년 인증서 투명성 로그는 세계 최대 CA였던 Symantec의 대규모 오발급을 포착함
  - 소유하지 않은 도메인의 인증서를 발급했으며 google.com 인증서도 포함됐음
  - 자체 보안 정책을 무시하고 정식 감사인이 아닌 사람의 감사 자료를 제출함
  - 오발급 인증서는 3만 개가 넘었음
- Google은 Symantec, VeriSign, Thawte, RapidSSL 브랜드에 대한 신뢰를 제거했고, 남은 사업은 DigiCert에 매각됨
  - CA/Browser Forum과 기존 감사가 찾지 못한 문제를 인증서 투명성 로그가 드러냄
대규모 감시와 완전 순방향 비밀성
- Edward Snowden이 공개한 자료에는 2007년 이후의 광범위한 감시 활동이 포함됨
  - PRISM은 Microsoft, Facebook, Apple 등 대형 기술 기업의 네트워크를 지나는 데이터에 접근함
  - 영국과 함께 진행한 Tempora는 백본 광섬유 통신을 기록함
  - 트래픽을 먼저 수집한 뒤 개인 키를 확보하거나 제출받아 과거 통신을 복호화하는 harvest now, decrypt later 방식이 실제로 추진됐음
- 기존 핸드셰이크는 하나의 장기 개인 키를 신원 증명과 암호화에 함께 사용함
  - 서버 개인 키를 나중에 얻으면 기록해 둔 키 교환 정보로 과거 통신까지 복호화할 수 있었음
- 2013년 도입된 완전 순방향 비밀성은 두 역할을 분리함
  - 인증서는 서버 신원을 증명함
  - 데이터 암호화에는 세션마다 새로 만든 일회성 Diffie-Hellman 키를 사용함
- 개인 키가 유출되면 서버 사칭 가능성은 남지만 과거 세션 전체를 복호화할 수는 없어 유출 피해 범위가 달라짐
Diffie-Hellman 키 교환 원리
- 클라이언트와 서버는 각각 비밀값 A와 B를 만들고, 공개된 G와 P를 이용해 계산한 중간값을 교환함
- 네트워크 관찰자는 G^A와 G^B를 볼 수 있지만 A와 B 자체는 알 수 없음
- 양쪽은 상대의 중간값과 자신의 비밀값으로 동일한 G^AB를 계산하지만, 관찰자가 공개 정보만으로 같은 값을 구하는 것은 계산상 비현실적임
- 공유 비밀 자체가 네트워크로 전송되지 않고 인증서 개인 키도 세션 암호 키 생성에 사용되지 않으므로, 나중에 개인 키를 얻어도 기록된 과거 통신을 복호화할 수 없음
인증서 투명성 로그
- Google은 2013년 RFC 6962로 인증서 투명성(Certificate Transparency, CT) 로그를 추진함
  - CA가 발급한 모든 인증서를 공개된 추가 전용 로그에 기록하도록 요구함
  - 특정 도메인의 인증서가 새로 발급되면 도메인 소유자와 브라우저 업체가 이를 감시할 수 있음
- Chrome은 CA의 합의를 기다리지 않고 2015년부터 EV 인증서에 CT를 요구했으며, 2018년에는 모든 인증서로 확대함
  - 로그에 기록하지 않은 인증서는 Chrome에서 신뢰하지 않는 방식으로 강제함
- CT 로그에서는 특정 도메인에 발급된 모든 인증서와 포함된 도메인, 발급자, 만료일을 검색할 수 있음
- 이런 공개성 때문에 기업의 비공개 하위 도메인이나 인증서에 포함된 개인 이메일 주소까지 열거할 수 있다는 부작용도 있음
SHA-1 폐기 지연
- SHA-1은 인증서 체인의 서명에 사용되던 해시 알고리듬이며, 서로 다른 입력이 같은 해시를 만드는 충돌 가능성이 2005년부터 경고됨
- 공격자가 정상 인증서와 대상 도메인 인증서가 같은 SHA-1 값을 갖도록 만들 수 있다면 CA는 문제를 알아채지 못한 채 부정한 인증서에 서명할 수 있음
- Microsoft는 2013년 SHA-1을 이론적 문제가 아닌 중대한 오류로 판단하고 2016년 이후 Windows에서 신뢰하지 않겠다고 발표함
- 연구는 충돌 가능성을 단계적으로 입증함
  - 2015년에는 시작 부분을 통제하는 free-start collision이 나옴
  - 2017년 Google의 SHAttered가 완전한 SHA-1 충돌을 입증함
- 당시 3년 인증서가 발급됐기 때문에 충돌이 입증된 뒤에도 2019년까지 유효한 SHA-1 인증서가 존재할 수 있었음
Heartbleed와 작동하지 않는 인증서 폐기
- 2014년 Heartbleed는 OpenSSL의 버퍼 오버플로 결함으로, 조작된 요청 한 번에 서버 메모리 최대 64KB를 반환하게 했음
  - 개인 키, 세션 토큰, 비밀번호 등이 포함될 수 있었고 요청을 반복할 수도 있었음
  - 인터넷 보안 서버의 17%가 취약했음
- 완전 순방향 비밀성을 사용한 서버는 개인 키가 노출돼도 과거 통신 전체가 복호화되지는 않았음
- 이를 사용하지 않은 서버는 해당 키로 보호된 과거 통신까지 노출됐다고 가정해야 했음
- 수십만 개의 인증서를 한꺼번에 폐기해야 했지만 기존 인프라는 이를 안정적으로 처리하지 못함
- 인증서 폐기 방식은 모두 한계를 보였음
  - CRL은 폐기된 인증서 전체를 파일로 배포해 크고 느리며 최신 상태를 유지하기 어려웠음
  - OCSP는 인증서 상태를 조회하는 API지만 서비스 장애가 잦고, 사용자가 방문하는 사이트가 CA에 노출되는 개인정보 문제가 있었음
  - OCSP stapling은 상태 응답을 TLS 요청에 포함하지만 구현이 어려워 널리 채택되지 않음
  - Chrome의 CRLSet과 Mozilla·Microsoft·Apple의 유사 체계는 중요한 폐기 정보 일부만 브라우저나 운영체제에 배포함
- revoked.badssl.com 은 브라우저에 따라 차단되거나 정상 로드될 수 있어 인증서 폐기가 일관되게 적용되지 않음을 보여줌
Let's Encrypt와 ACME 자동화
- Mozilla와 EFF에서 진행되던 무료 CA와 자동 발급 프로토콜 작업은 비영리 조직 ISRG 아래에서 합쳐짐
  - Let's Encrypt는 CA이며 ACME는 인증서 발급을 자동화하는 프로토콜임
  - 무료 단기 인증서를 사람의 개입 없이 발급하고 갱신하는 것이 목표였음
- ACME 클라이언트가 CA에 인증서를 요청하면 도메인 제어권을 증명할 도전 과제를 받음
  - DNS에 _acme-challenge TXT 레코드를 추가함
  - 또는 /.well-known/acme-challenge 경로에 지정된 파일을 제공함

- 초기 CA들은 기업이 이 방식을 처리하지 못할 것이라고 반대했지만, 10년 뒤 전체 인증서의 60% 가 Let's Encrypt에서 발급되고 매일 수백만 건이 갱신됨

브라우저가 CA의 거부권을 무력화한 과정
- Google은 2017년 인증서 유효기간을 당시 3년에서 1년으로 줄이자고 제안함
  - 브라우저들은 찬성했지만 Let's Encrypt를 제외한 CA들이 반대해 합의 요건을 충족하지 못함
  - 당시 대형 CA Entrust 고객의 92%가 수동 프로세스를 사용했음
- Chrome은 2018년 HTTPS가 아닌 사이트에 Not Secure 표시를 도입함
  - 보안 연결 채택률이 약 1년 만에 40%에서 97%로 상승함
- Apple과 Google은 2019년에도 1년 유효기간을 제안했지만 CA의 반대로 다시 실패함
- Apple은 2020년 2월 투표 없이 398일을 넘는 인증서를 신뢰하지 않겠다고 발표함
  - iPhone에서 작동하려면 따라야 했으며 사설 PKI 인증서에도 적용됨
  - CA들은 합의 절차를 훼손한다고 반발했지만 Apple은 변경을 기다릴 수 없다는 입장이었음
- 이후 기존 Baseline Requirements를 현실에 맞추는 표결이 15대 4로 통과함
  - CA가 계속 거부하면 브라우저 업체들이 Forum을 떠나 각자 별도 규칙을 적용할 수 있었음
  - 그 경우 CA는 브라우저별 감사를 따로 받아야 해 비용 부담이 크게 늘어날 수 있었음
- Forum은 유지됐지만 실질적인 정책 주도권은 CA에서 브라우저 업체로 이동함
TLS 1.3과 장기 인증서 위험 축소
- 2018년 출시된 TLS 1.3은 이전 공격과 취약점에서 얻은 교훈을 반영함
  - 암호 스위트를 37개에서 5개로 줄임
  - 공격 표면을 넓히던 프로토콜 기능을 제거함
  - 완전 순방향 비밀성을 의무화함
  - 프로토콜 구성의 약 절반을 제거함
- 2018년 Defcon에서는 도메인을 판매한 뒤에도 이전 소유자가 유효한 인증서를 보유하는 bygone SSL 문제가 다뤄짐
  - 소유자와 인증서 보유자가 다른 도메인이 150만 개를 넘었음
  - stripe.com의 이전 소유자가 도메인 판매 후에도 3년간 유효한 여러 인증서를 보유한 사례가 포함됐음
  - 인증서 유효기간을 45일로 줄이면 이 위험을 95% 줄일 수 있다는 연구 결과가 나옴
47일 인증서 시대
- Apple, Google, Microsoft가 합의한 일정에 따라 인증서 최대 유효기간은 단계적으로 단축됨
  - 2026년 3월부터 200일
  - 2027년부터 100일
  - 2029년부터 47일
- 기존 398일 인증서는 연 1회 작업으로 관리할 수 있었지만 200일은 약 연 2회, 100일은 약 연 5회, 47일은 약 연 10회의 갱신이 필요함
- 인증서 50개를 수동으로 관리하면 2029년에는 연간 약 500회의 갱신을 처리해야 하므로 부수 업무로 유지하기 어려움
발급 자동화보다 어려운 배포 자동화
- 인증서를 자동 갱신해도 새 인증서를 필요한 서버와 장치에 배포하지 못하면 장애가 발생함
- Fortnite의 인증서 만료 사고에서는 12분 만에 문제를 발견하고 인증서를 갱신했지만 완전 복구까지 5.5시간과 25명이 필요했음
  - 갱신 자체는 자동화됐지만 모든 서버와 장치에 배포하는 과정은 수동 작업에 크게 의존함
- 실제 배포에는 대상별 인증서 형식 변환, 올바른 위치로의 복사, 서비스별 재적용 또는 재시작 명령이 필요함
- Certbot, ACME 클라이언트, acme.sh만으로 시작한 자동화도 환경이 복잡해지면 자체 관리 시스템으로 확대됨
  - 단일 웹 서버에서는 cron 작업으로 충분할 수 있음
  - Tomcat은 Java KeyStore 변환과 배포 스크립트가 필요함
  - 와일드카드 인증서는 DNS 자격 증명을 스크립트에서 관리하게 만들 수 있음
  - Exchange나 웹 클러스터에서는 여러 노드가 인증서를 공유해야 함
  - 잘못된 Nginx 설정, 재시작 실패, 오래된 인증서 때문에 심야 장애가 발생할 수 있음
  - 이후 모니터링과 인증서 소유자·관리 절차를 기록한 스프레드시트가 추가됨
- 복잡한 인증서 스크립트는 장애를 하나씩 해결하는 과정에서 불완전하고 느리며 버그가 많은 수명주기 관리 시스템으로 변하기 쉬움
- 단순하지 않은 환경에서는 인증서 검색, 발급, 배포, 모니터링과 소유권을 통합 관리하는 체계가 필요함
포스트양자 암호 전환
- 양자 컴퓨팅은 Diffie-Hellman 키 교환을 깨뜨릴 것으로 예상되므로 현재의 완전 순방향 비밀성도 장기적으로 충분하지 않을 수 있음
- NSA를 비롯한 조직들이 미래의 양자 컴퓨터로 복호화하기 위해 트래픽을 다시 기록하고 있을 가능성이 있으나 확정된 사실은 아님
- NIST는 포스트양자 암호 표준을 공식화했지만 아직 대규모 운영에 사용할 수 있는 단계는 아님
- 향후 몇 년 안에 인증서를 새로 발급하고 소프트웨어를 변경하는 또 한 번의 전환이 필요함
- 인증서 수명주기를 자동화해 두면 포스트양자 전환을 설정 변경으로 처리할 수 있지만, 수동 체계에서는 장기간의 긴급 마이그레이션이 될 수 있음
