- 폐쇄형 모델은 높은 최저 성능과 단순한 개발 환경을 제공하지만 성능 상한이 낮을 수 있으며, 자체 스택은 더 많은 작업과 낮은 초기 성능을 감수하는 대신 도메인 특화 성능의 상한을 높일 수 있음

- Alex Karp는 기업에 생산수단을 소유하라고 촉구했고, Satya Nadella는 프런티어 연구소의 지능을 구매하면 비용뿐 아니라 이를 유용하게 만드는 독점 지식까지 제공하므로 두 번 지불하는 셈이라고 봄
- 기업이 답해야 할 핵심 질문은 사업의 중심에 있는 지능을 누가 소유할 것인가임
- 자체 지능 구축이 프런티어 연구소와의 결별을 뜻하지는 않음
  - 많은 워크로드에서는 프런티어 API와 에이전트가 여전히 적합함
  - 다만 일부 기업은 특정 제품 영역에서 자체 AI 역량을 구축하고, 모델 웨이트를 직접 소유·조정하는 방향으로 수직 통합하고 있음
- Sequoia가 AI 창업자와 개발자를 모은 행사에서는 Harvey가 고객 관점의 접근법을 소개하고, Mercor·LangChain·Trajectory·Fireworks가 사후 학습 스택의 기술 구성요소를 다룸
자체 지능 구축이 가능해진 이유
- 오픈 웨이트 프런티어가 예상보다 빠르게 발전함
  - Kimi K3와 GLM 5.2는 프런티어에 가까운 출발점을 제공함
  - 과거에는 수개월간 미세 조정하더라도 다음 프런티어 모델이 출시되면 그간의 성능 향상이 무효화될 수 있었음

  - 강력한 평가와 하네스 엔지니어링, 사후 학습, 온라인 학습을 결합하면 오픈 모델이 특정 도메인에서 프런티어 모델보다 나은 성능을 낼 수 있음
- 과거에는 성능을 양보할 수 있을 때 오픈 웨이트를 선택했지만, 이제는 제품의 생존과 전략에 영향을 미치는 선택이 됨
- 경쟁의 초점은 모델 웨이트나 제품을 넘어 지능 계층 자체로 이동하고 있음

  - 모델을 소유하면 사용량 증가에 따른 비용 구조를 바꿔 마진을 보호할 수 있음

독점 데이터
  - 피드백·평가·고객 상호작용·도메인 데이터가 시스템 성능을 높이는 핵심이라면 해당 데이터를 조직 내부에 유지할 필요가 있음

제품 통제권
  - 애플리케이션 계층과 지능 계층의 경계가 흐려지고 있음

  - Harvey Research·RampLabs·Glean·Factory 등이 이 방향으로 움직이고 있음
실행 조직과 외부 신뢰 구축
- 자체 지능 구축을 기존 플랫폼 팀에 억지로 맡기기보다 공격적으로 실험하는 전담 팀을 구성해야 함
  - 평가 구축
  - 데이터 설계
  - 오픈 모델 실험
  - 하네스 조정
  - 특정 도메인의 성능 개선
- 새로 꾸린 소규모 팀도 여러 생태계 파트너와 협력하면 상당한 연구를 수행할 수 있음
  - Harvey는 연구팀 7명으로 많은 연구를 진행함
- 구매자는 채택할 AI 공급자를 직접 고르며, 공개 연구·벤치마크·기술 게시물이 비슷한 후보 간 선택을 가르는 기준으로 작용함
- 내부에서 유용한 연구를 수행했다면 생태계에 공개해 기술 역량을 확인할 수 있게 해야 함
1단계: 반복 가능한 평가 구축
- 평가는 시스템이 실제 작업을 얼마나 잘 수행하는지 측정하는 과제 집합임
  - 각 과제는 프롬프트, 모델이 사용할 컨텍스트, 채점기로 구성됨
- 초기에는 창업자가 출력을 직접 살펴보고 감으로 품질을 판단하는 경우가 많으며, 이를 반복 가능한 판단으로 바꾸는 것이 목표임
- Harvey의 Legal Agent Benchmark는 실제 법률 업무를 모델이 수행할 수 있는 개별 과제로 변환함
  - 첫 버전은 24개 법률 실무 분야에 걸쳐 1,200개 이상의 에이전트 과제를 포함함
  - 전문가가 작성한 75,000개 이상의 루브릭 기준으로 평가함
- 자체 지능을 구축할지 결정하기 전에 평가 체계부터 준비해야 함
- 모든 순전파 결과에 평가를 적용하면 모델 선택을 추측이 아닌 측정 가능한 결정으로 바꿀 수 있음
2단계: 하네스와 컨텍스트 설계
- 에이전트는 모델·컨텍스트·하네스의 세 부분으로 구성됨
- 하네스는 모델 주변의 제품 로직을 관리함
  - 라우팅
  - 검색
  - 도구
  - 메모리
  - 폴백
  - 실행 추적
- 하네스의 주된 역할은 적절한 시점에 필요한 컨텍스트를 모델에 전달하는 것임
- 작업이 모델의 학습 분포에서 멀어질수록 범용 하네스의 성능은 떨어짐
- 잘 설계된 하네스는 요청을 작업에 가장 적합한 모델로 보내고, 여러 모델에 동일한 평가를 재사용하며, 에이전트에 제공할 컨텍스트와 도구를 결정함
- 관찰 가능성도 확보할 수 있음
  - 어떤 컨텍스트가 입력됐는지 추적함
  - 어떤 도구가 호출됐는지 확인함
  - 에이전트가 어느 지점에서 막혔는지 파악함
3단계: 목적에 맞는 사후 학습 선택
- 사후 학습 기법은 개선하려는 문제에 맞춰 선택해야 함
  - 사실이 부족하면 사후 학습 대신 컨텍스트나 RAG를 사용함
  - 출력 형식이나 행동이 잘못됐다면 지도 미세 조정을 적용함
  - 제품의 취향과 선호를 반영하려면 선호도 조정을 사용함
  - 전문 작업 능력을 개선하려면 강화학습을 활용함
  - 모델이 너무 느리거나 비싸다면 증류함
- 평가 결과를 개선할 수 있는 가장 가벼운 방법부터 선택하는 것이 목표임
- 조정된 모델도 동일한 하네스로 서비스하면서 품질·지연 시간·비용을 측정해야 함
4단계: 프로덕션 경험을 학습 루프로 전환
- 평가·하네스·모델이 준비되면 프로덕션에서 전체 시스템을 지속적으로 개선해야 함
- 모델은 계속 똑똑해지지만 매 세션을 첫 출근 날처럼 시작함
  - 뛰어난 지능을 갖췄더라도 특정 조직과 업무에서 곧바로 최고의 성과를 내지는 못함
  - 부족한 것은 지능보다 경험이며, 에이전트가 작업하는 과정에서 그 경험이 생성됨
- 궤적(trajectory)은 작업 수행의 전체 경로를 뜻함
  - 모델이 본 컨텍스트
  - 호출한 도구와 하위 에이전트
  - 생성한 답변
  - 사용자가 수정·취소·재시도한 행동
- LangChain의 LangSmith 같은 도구로 궤적을 수집해야 지속적인 프로덕션 학습 루프를 만들 수 있음
  - 실패한 작업은 새로운 평가가 됨
  - 누락된 정보는 컨텍스트나 메모리에 추가됨
  - 잘못된 도구 응답은 하네스 수정으로 이어짐
자체 스택의 비용과 성능 상한
- 폐쇄형 모델 스택은 프런티어 모델을 호출하고 Claude Code나 Codex 같은 기성 하네스에 프롬프트와 컨텍스트를 추가해 출시할 수 있어 단순함
- 이 방식은 높은 최저 성능을 제공하지만 성능 상한도 낮을 수 있음
- 자체 지능 스택에서는 더 많은 시스템을 직접 운영해야 함
  - 프로덕션 스택은 오픈소스 모델, 맞춤 하네스, 도구, 컨텍스트로 구성됨
  - 개발 스택은 독점 평가, 도메인 데이터, 온라인 학습 루프로 구성됨
- 더 많은 작업이 필요하고 초기 최저 성능이 낮아질 수 있지만, 특정 제품과 도메인에서 도달 가능한 성능 상한은 높아짐
- 프런티어 연구소가 만드는 대형 모델을 계속 활용하면서, 제품 기업은 빠르고 뚜렷한 성향을 가지며 도메인 작업에 맞춰진 소형 모델을 함께 키울 수 있음
- 더 많은 기업이 자체 지능을 소유하면 서로 다른 제품 특성이 유지되고 AI 생태계의 다양성도 커질 수 있음

## 텔레그램 수집 시 유의사항

- 이 컬렉터는 공개 웹 미리보기(t.me/s/{channel})만 수집하며, 비공개 채널 수집은 이 단계에서 구현하지 않는다.
- 웹 미리보기는 페이지당 최대 20개 메시지씩, 최대 10페이지(최근 약 200개)까지만 페이지네이션한다.
