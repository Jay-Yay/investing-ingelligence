### LLM 시대의 프로그래밍 학습 | GeekNews

(https://news.hada.io/topic?id=33794)

- LLM으로 상당한 규모의 시스템을 만든 초보 개발자가 구현 능력과 이해 수준의 격차에 부딪힘. 작동할 때는 보이지 않던 격차가 제품화와 오류 수정 과정에서 드러남
- 개발자는 오래전부터 완전히 이해하지 못하는 추상화 위에서 일해 왔으며, 실용적인 기준은 자신이 일하는 계층의 바로 위와 아래를 이해해 대부분의 문제를 해결할 수 있게 하는 것임
- 기초를 체계적으로 익히는 방식은 과거에는 효과적이었지만, 수십 년에 걸쳐 실력을 쌓을 시간이 지금 입문자에게도 있을지는 불확실함. LLM이 질문을 도와줘도 사람이 지식을 흡수하는 속도에는 한계가 있을 수 있음
- AI가 프로그래머를 비롯한 지식 노동자의 일자리를 대체할 가능성에는 경제적 불확실성이 따름. 과거 기술 발전이 새 일자리를 만들었다고 해서 일자리를 잃은 사람들이 그 혜택을 받은 것은 아님
- LLM에는 “다음에 무엇을 배울까?”보다 “이 코드를 더 간결하게 만들 수 있을까?”처럼 답을 직접 검증할 수 있는 질문을 선호하며, 실제로 작동하고 더 짧아졌는지 확인하는 방식으로 활용함
AI로 만든 시스템과 이해의 격차
- 정규 컴퓨터과학 교육을 받지 않은 한 독자가 약 1년 동안 LLM을 활용해 TypeScript/JavaScript 시스템을 구축함
  - API, PostgreSQL, LLM 파이프라인, 연구 자동화, 여러 모델을 활용하는 작업 흐름을 포함함
  - 초기에는 아이디어와 구현 사이의 거리가 극적으로 줄어드는 경험을 함
- 실제 프로덕션 제품으로 전환하면서 이해하지 못하는 동작과 연쇄적인 오류에 부딪힘
  - AI로 오류 하나를 고치면 다른 오류가 생겼고, 수개월간 리팩터링한 뒤 시스템이 자신의 이해 수준을 넘어섰음을 깨달음
  - 다른 모델에 묻지 않고는 다음 행동을 결정하기 어려운 순간도 있었음
  - 작동하는 제품을 만든 것인지, 충분히 이해하고 책임질 수 없는 제품의 외형을 만든 것인지 의문을 품음
- AI를 거부하는 것이 아니라, AI와 전문적으로 일하고 싶지만 어떤 관계를 맺어야 할지 불확실한 상황임
- 이에 대한 조언 역시 상황의 불확실성을 전제로 하며, 엄밀하거나 불변하는 정답은 아님
AI에 대한 양가감정과 고용의 불확실성
- AI에 대한 태도는 아직 확정적이지 않지만, 좋아하지 않는 쪽으로 기울어 있음. 직접 사용하고 실험하면서 감탄과 좌절을 모두 경험함
  - 성능이 나쁠 때는 30년 넘게 익힌 기술이 여전히 유효하다는 위안을 얻음
  - 가장 뛰어난 성능을 보일 때 오히려 가장 강한 반감을 느끼며, Butlerian jihad에 참여하고 싶다는 생각까지 듦
- 개인적으로는 나이와 그동안의 성취 덕분에 실업을 견딜 수 있겠지만, 지식 기반 사회 전체가 같은 충격을 견딜 수 있을지는 불확실함
  - 프로그래밍은 보험금 청구 관리 같은 업무보다 검증이 쉬울 수 있어, 다른 사무직보다 먼저 일자리가 줄어들 가능성이 있음
  - 경제학을 공부한 입장에서 30~40%의 대규모 실업이 경제에 상당한 영향을 주지 않을 상황은 상상하기 어려움
  - 이는 확정적인 실업률 전망이 아니라 대규모 실업이 발생할 경우에 대한 우려임
- 기술 발전이 새 일자리를 만든다는 역사적 논거만으로 모든 것이 괜찮아질 것이라 낙관하기는 어려움
  - 양말 편직기, 증기기관, 내연기관, 컴퓨터는 새 일자리를 만들었지만, 그 일자리가 기존 일자리를 잃은 사람들에게 돌아간 것은 아님
  - 탄광 노동자가 하루아침에 프로그래머가 되지는 않았음
  - 중국의 세계무역기구 가입 때도 비슷한 논리가 쓰였고 많은 일자리가 생겼지만, 서구에서 생긴 것은 아니었음
- 이런 회의가 틀리기를 바라며, 앞으로 10년 이상 프로그래밍을 계속하고 싶은 마음과 이제 성인이 된 자녀들의 미래에 대한 바람도 있음
지금 기초를 배워야 하는가
- LLM 이전에 익힌 프로그래밍 기초는 30년 동안 유용했음
- 지금 처음 진로를 정한다면 목공, 금속 가공, 총기 제작처럼 손과 눈의 협응이 필요한 직업도 진지하게 고려할 수 있음
  - 로봇공학도 발전하고 있지만, 육체노동의 대체는 더 먼 미래에 있을 것으로 봄
- 현재도 대학 과정에서 자료구조와 언어 의미론 등을 공부하고 있으나, 큰 금전적 보상보다 호기심이 동기임
- AI가 이해 속도보다 빠르게 개발하도록 만드는지는 아직 판단하기 어려움. 개발자는 수십 년 동안 자신이 완전히 이해하지 못하는 추상화 계층 위에서 일해 왔음
  - 웹 개발자가 컴파일러 프로그래밍을 잘 아는 것은 아니며, 컴파일러 개발자가 집적회로 설계를 잘 아는 것도 아님
  - 집적회로 설계자 역시 자신보다 위에 있는 추상화 계층을 잘 알지 못할 수 있음
- 실용적인 경험칙은 현재 작업하는 계층의 바로 아래와 바로 위를 이해하는 것이며, 이를 통해 대부분의 문제를 해결할 수 있었음
경험자의 적응과 초보자의 기초 학습은 다름
- 탄탄한 기초를 가진 개발자는 낯선 환경에서도 기존 지식을 활용해 적응할 수 있음
  - 예를 들어 RISC-V 어셈블리로만 작성된 애플리케이션을 유지보수하는 일은 매우 낯설고 어렵겠지만, 프로그래밍 자체를 처음 배우는 사람보다는 덜 어려움
  - 작은 RISC-V 연습 프로그램과 RISC-V 코드를 생성하는 연습용 컴파일러를 작성한 경험도 활용할 수 있음
- 초기 경력에서는 일을 완수하는 것과 일하면서 배우는 것을 동시에 해 나갔음
  - 1999년부터 C++로 COM 컴포넌트를 작성하면서도 내부 동작을 많이 이해하지 못했음
  - 그럼에도 작동하는 결과물을 만들고 눈에 띄는 메모리 누수를 제거하는 수준에는 도달함
- 이해 없이 조합하는 데 만족하지 못해 한발 물러나 기초를 체계적으로 공부했으며, 1990년대 중반에 시작한 경력에는 이 방식이 잘 맞았음
- 같은 방식이 오늘날에도 잘 맞을지는 확신하기 어려움
  - 과거의 자신감이 무지를 인식하지 못한 상태였음을 Dunning-Kruger 효과에 비춰 알아차릴 수준까지 성장하는 데 수십 년이 걸렸음
  - 지금 배우는 사람에게도 그만큼의 시간이 있는지는 불확실함
- LLM은 더 구체적인 질문을 할 수 있게 해 학습을 빠르게 도울 수 있음
  - 30년 전에는 도움이 될 내용을 기대하며 책을 샀고, 당장 필요한 일과 관련 없는 자료도 많이 읽어야 했음
  - 다만 인간의 학습 속도를 크게 높일 수 있을지는 의문임. 병목은 교사나 자료보다 뇌가 새 지식을 흡수하는 속도에 있을 수 있음
언어를 배워 온 방식과 현재의 학습
- 초기 학습은 느린 시행착오가 중심이었고, 때때로 책의 도움을 받음
- 아주 이른 시기의 COMAL 80 시도 이후, 경제학 석사 논문을 위한 분기 다이어그램과 로렌츠 끌개 재계산이 첫 프로그래밍 프로젝트였음
  - 당시 사용할 수 있던 QBasic으로 작성함
  - 함께 제공된 예제를 공부하고 가끔 친구에게 질문함
- 1990년대와 2000년대에는 주로 예제와 문서로 학습함
- 지금은 많은 언어를 접한 경험 덕분에 보통 기존 코드를 읽고 불명확한 부분을 찾아보는 방식으로 새 언어를 익힐 수 있음
  - 이 방식은 2026년에 처음 프로그래밍을 배우는 사람에게 그대로 적용하기 어려움
  - 일반적인 언어라는 전제가 있으며, APL을 다시 배우려면 적어도 튜토리얼이 필요함
LLM에는 검증 가능한 질문을 하기
- LLM의 답변을 깊이 신뢰하지 않으므로 학습에 많이 활용하지는 않음. LLM의 문제를 환각보다 진실에 무관심한 발화로 보는 태도가 바탕에 있음
- 그렇다고 LLM을 쓰지 않는 것은 아니며, 검증 가능한 답변을 내는 질문을 선호함
  - “이 Haskell 표현식을 더 간결하게 만들 수 있는가?”라는 질문에는 코드 제안이 나올 수 있음
  - 제안한 코드가 작동하는지, 실제로 더 짧은지는 쉽게 확인할 수 있음
- “다음에는 무엇을 배워야 하는가?”는 같은 방식으로 답을 검증하기 어려워 LLM에 잘 묻지 않음
- LLM 활용의 기준은 반증 가능성이 있는 질문을 하는 것임
