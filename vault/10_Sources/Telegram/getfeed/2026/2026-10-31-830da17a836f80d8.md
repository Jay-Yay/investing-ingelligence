  - 반복적으로 쓰는 분석 패턴과 추론 논리를 프롬프트나 모델에 반영할 수 있다는 가설이 있지만, 답은 아직 명확하지 않음

SQL 생성만으로는 분석 능력을 측정할 수 없음
- 평가 대상인 데이터 에이전트는 여러 데이터베이스와 기존 분석 도구를 사용해, 사람이 맡을 법한 비즈니스 질문에 답하는 주니어 분석가에 가까움

- 기존 텍스트-SQL 변환 벤치마크는 실제 분석 업무보다 범위가 좁음

- 테이블 질의응답 방식은 CSV나 테이블 전체를 모델 문맥에 넣지만, 실제 데이터는 문맥 창보다 크며 비용도 발생함
  - 관계대수로 처리할 수 있는 질의라면 데이터베이스를 사용하는 편이 적절함

- 다만 LLM이 문맥 안에서 열 선택, 필터링, 조인을 수행할 수 있는지는 별개의 흥미로운 연구 문제임
  - 긴 문맥에서 특정 정보를 찾는 평가보다 관계 연산 능력을 묻는 평가가 더 흥미로울 수 있음
  - 모든 토큰 쌍을 다루는 모델의 계산 방식은 일반 프로그램의 관계 연산과 다르며, 그 이론적 특성을 충분히 이해하지 못하고 있음

- 벤치마크는 실무자와의 대화를 바탕으로 여러 데이터베이스가 공존하는 환경을 반영함
  - 서로 다른 저장소에서 데이터를 가져와 계산하거나 조인해야 함

- 시맨틱 레이어는 여전히 사람이 내용을 이해하고 관리해야 하는 어려운 작업임
  - 에이전트가 생성했다고 해서 품질 기준이 낮아지는 것은 아님
  - 에이전트를 잘 활용하면 구축이 조금 쉬워질 수 있지만, 부정확한 레이어는 후속 분석에도 영향을 줌
- 원시 데이터에 바로 연결하면 시행착오가 많을 가능성이 높고, 정제된 골드 테이블과 시맨틱 레이어를 제공하면 더 나은 결과를 기대할 수 있음
  - 다만 잘 정리된 골드 테이블을 갖춘 곳은 많지 않음
  - 같은 조직 안에서도 깨끗하게 정리된 일부 데이터와 방대한 원시 데이터가 공존하므로, 적용 범위를 구분해야 함

- 「Who Validates the Validators」 는 LLM 심판을 없애자는 연구가 아니라, 개발자가 평가 결과를 신뢰하도록 만드는 과정을 탐구함
  - 주관적이고 평가하기 어려운 기준을 대규모로 적용하려면 LLM 심판이 필요함
  - GPT-4 출시 직후 사용자 연구를 수행했으며, 이후 LLM 심판은 학습과 강화학습 등에도 널리 쓰이게 됨
- 능동 학습과 대화형 머신러닝을 활용해, 개발자의 실시간 라벨로 평가 프롬프트를 합성하는 방식을 실험함
  - 처음부터 대량의 정답 라벨을 준비하기는 어렵지만, 인터페이스에서 결과를 보며 라벨을 붙일 수는 있음
  - LLM 파이프라인 구축 도구인 ChainForge 위에 프로토타입을 만듦
- 예상 밖의 장애물은 평가 기준 변화였음
  - 사람은 결과를 충분히 보기 전까지 무엇을 원하는지 명확히 알지 못함
  - 출력을 보며 문제 영역을 새로 이해하거나, 모델이 잘하는 작업을 발견하면서 기준을 바꿈
  - 상품 리뷰 요약에서 모델이 특정 측면을 예상보다 잘 요약한다면, 그 장점을 활용하도록 평가표를 바꿀 수도 있음
- LLM 심판을 신뢰하려면 먼저 사람이 충분한 표본을 직접 확인하고 평가표에 확신을 가져야 함
  - 데이터와 AI뿐 아니라, 사람이 결과를 해석하고 의사결정하는 HCI 문제까지 연결됨
사람의 반응을 얻는 폐쇄형 평가 루프
- Meta의 광고망은 AI 생성 결과에 대한 사람의 반응을 다시 측정할 수 있는 평가 구조의 사례임
  - 콘텐츠를 생성하고 배포한 뒤 어떤 결과가 사람의 상호작용을 유발하는지 확인할 수 있음
- 이런 구조에는 배포 수단과 피드백 확보 능력이 함께 필요함
  - 모든 광고 사업자가 같은 조건을 갖추는 것은 아님
  - AI 출력에 대한 사람의 피드백을 어떻게 얻을 것인지가 사업 모델 차원의 질문이 될 수 있음
새 모델이 나오면 평가가 필요 없어질까?
- 「Defense of AI Evals」 는 새 모델이 충분히 좋아졌으니 평가를 하지 않아도 된다는 온라인 논쟁에서 출발함
  - 평가와 프롬프트 개선에 공들인 것보다 다음 모델을 기다리는 편이 성능 향상에 더 도움이 됐다는 실망이 논쟁의 한 원인으로 보임
- Shreya의 경험에서는 새 모델이 품질과 비용의 파레토 경계를 가장 크게 이동시킴
  - 최종 사용자가 할 수 있는 프롬프트 조정과 하네스 개선도 유용하지만, 개선 폭에는 한계가 있음
- 최근 성능 향상 중 모델과 하네스의 기여도를 명확히 나누기는 어려움
  - 서로 다른 모델의 차이는 여전히 크며, 충분히 사용해야 드러나는 경우도 있음
  - 모델별 강점은 과제에 따라 들쭉날쭉하고, 반복적인 작업에는 더 작은 모델로 충분할 수 있음
  - 사용자는 전체 과제 공간의 일부만 경험하므로 자신의 경험만으로 일반화하기 어려움
실무 평가의 출발점은 출력 직접 보기
- 데이터 분석에서 익숙한 “데이터를 직접 보라”는 원칙은 에이전트 평가에도 그대로 적용됨
  - 출력을 보지 않고서는 에이전트가 무엇을 하는지 제대로 판단하기 어려움
- 구조화된 데이터의 탐색적 데이터 분석(EDA) 은 비정형 에이전트 출력에 그대로 옮겨지지 않음
  - 데이터프레임 요약이나 이상치 탐지처럼 널리 쓰이는 기능에 대응하는 도구가 부족함
  - 현재는 스프레드시트에서 LLM 출력을 행별로 읽고 평가표를 만든 뒤, 다른 LLM 심판의 결과를 다시 읽는 식으로 작업하는 경우가 많음
- 당장은 행별 검토를 생략하지 않고 체계적으로 수행하는 것이 좋음
  - 기존 EDA 기법을 응용해 출력을 임베딩하고 군집화해 볼 수 있음
  - 다만 임베딩이 출력의 중요한 특성을 잘 표현한다는 보장이 없고, 해석도 어려워 구조화된 데이터 군집화만큼 명확하지 않음
  - 필요한 처리 코드를 직접 작성해야 하는 등 도구의 미성숙함이 남아 있음
AI SQL의 비용과 전용 추론 엔진
- Snowflake, Google BigQuery, Databricks는 SQL 안에서 AI 연산자를 사용하는 기능을 제공함
  - 특정 방식으로 제품에 불만을 표현한 고객 리뷰를 필터링하는 등, 비정형 데이터 해석을 질의 안에 넣을 수 있음
  - 유용하지만 질의 비용이 수십만 달러로 커지는 사례도 있어 최적화가 중요함
- 현재 구현의 주요 문제는 행별 LLM 호출임
  - 각 행의 프롬프트를 별도 HTTP 요청으로 외부 모델에 보내는 방식은 비용이 큼
  - 집계 시 표본 추출을 하거나 작은 모델을 쓰면 호출 비용을 줄일 수 있지만, 여전히 행 단위 호출 구조에 머무름
- 진행 중인 연구는 AI SQL 전용 추론 엔진을 만드는 것임
  - 공개 모델의 성능 향상을 활용하고, 질의 계획과 논리적 재작성을 추론 실행에 연결하려 함
  - AI 연산을 가능한 한 프리필(prefill) 중심으로 만들고 디코딩을 없애는 방향을 탐구함
  - 대규모 실행과 필요한 모델 지원도 과제임
- 인프라 측면의 장애물은 데이터베이스와 GPU가 보통 함께 배치되지 않는다는 점임
  - AI 활용이 데이터베이스 가까이에 GPU를 두는 계기가 되기를 기대하지만, 아직 확정된 변화는 아님
- 데이터 분야의 AI 수요를 단순한 모델 호출로만 구현하는 데서 벗어나, 데이터베이스 내부 구조와 질의 최적화 전문성을 결합해야 함

## 텔레그램 수집 시 유의사항

- 이 컬렉터는 공개 웹 미리보기(t.me/s/{channel})만 수집하며, 비공개 채널 수집은 이 단계에서 구현하지 않는다.
- 웹 미리보기는 페이지당 최대 20개 메시지씩, 최대 10페이지(최근 약 200개)까지만 페이지네이션한다.
- 이미지, 동영상 등 미디어 전용 메시지(텍스트 없음)는 캡처하지 않는다.
- 메시지에 포함된 기사 링크(최대 메시지당 3개, 유튜브/X/인스타그램/페이스북 제외)는 본문을 함께 가져와 아래 '첨부 기사 원문'에 붙인다 - 실패하면 그 링크만 오류로 표시된다.
