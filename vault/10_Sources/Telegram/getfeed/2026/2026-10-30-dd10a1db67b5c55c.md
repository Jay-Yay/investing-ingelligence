PHP2Shell에서 커널 권한 상승까지
- 회수한 PHP2Shell 구현체는 알려진 공개 익스플로잇의 복사본이 아닌 맞춤형 비공개 빌드임
  - 기본 원리는 같지만, 해당 방화벽 플랫폼에 맞춰 독립적으로 개발한 것으로 보임
  - appweb 관리 서버의 PHP session.upload_progress 메커니즘을 공격하며, PHP 8.0.30과 높은 메모리 한도가 메모리 손상 단계의 실행을 가능하게 함
- 원격 코드 실행은 네 단계의 메모리 조작으로 진행됨
  - A1, 메모리 고갈: 약 383MB 규모의 조작된 multipart POST 요청으로 거대한 파일명과 세션 진행 데이터를 보내 예측 가능한 메모리 배치를 유도함
  - B1, 정보 유출: A1에서 남은 오래된 세션 ID의 길이를 위조해 범위 밖 읽기를 일으키며, Set-Cookie 응답 헤더로 유출된 포인터에서 실행 중인libphp.so 의 기준 주소를 확보함
  - A2, 오래된 참조 준비: 약 500MB의 추가 메모리 압박으로 http_session_vars 를 살아 있는zend_reference 로 남긴 뒤, 두 번째 메모리 부족을 통해mod_data=NULL 상태를 만듦
  - B2, 코드 실행: 해제된 메모리 영역에 PHP HashTable 항목을 위조하고 pDestructor 가zif_system 을 가리키게 해, 정리 처리 과정에서nobody 사용자 권한으로 명령을 실행함
- nobody 권한만으로는 SELinux의httpd_t 제한 때문에 시스템 파일을 수정할 수 없어, Linux 커널 XFRM ESP-in-TCP 하위 시스템의 Fragnesia 취약점을 연계함
  - 페이지 캐시 쓰기로 /etc/pam.d/su 의 인증 규칙을 모든 인증을 허용하는pam_permit.so 로 덮어씀
  - 774바이트인 PAM 파일을 정밀하게 수정하기 위해 바이트 단위 스플라이싱 변형을 사용하며, 이후 비밀번호 없이 su root 가 성공함
- 두 익스플로잇은 최종 B2 HTTP 요청에서 함께 실행되며, 인증 없는 HTTPS 연결부터 지속적인 루트 웹셸 확보까지 전체 과정은 15분 미만에 완료됨
버전별 실험과 메모리 프로파일
- 공격은 어떤 버전에도 그대로 통하는 단일 페이로드가 아니라, OS 버전별 정확한 메모리 오프셋에 의존함
  - zval_ptr_dtor ,zif_system 주소, HashTable 구조 크기, 단계별 힙 배치를 제어하는 메모리 파라미터가 필요함
- 회수한 JSON 버전 프로파일은 11개이며, 실험 수준이 서로 다름
  - 구형 분기의 PHP 7.4.33용 임시 프로파일 2개는 기본 빌드와 핫픽스 변형에 해당함. 실험실에서 nobody 권한의 원격 코드 실행은 확인했지만 전체 공격 체인은 보정하지 못함
  - 신형 분기의 PHP 8.0.30용 프로파일 9개 중 1개는 보정을 완료했고, 8개는 기본 프로파일의 메모리 배치를 상속하거나 인접 빌드와 오프셋을 공유하는 임시 프로파일임
- 각 프로파일에는 해당 버전의 libphp.so 에서 추출한 오프셋, 라이브러리 SHA256, ELF 빌드 ID, 청크 크기와 채우기/비우기 횟수, 스프레이 오프셋 등이 들어 있음
  - 보정 완료 프로파일은 해당 버전의 실행 중인 VM에서 메모리 배치가 작동함을 확인한 상태임
  - 임시 프로파일은 바이너리에서 오프셋을 계산했지만 실제 실행 환경에서는 검증하지 않은 상태임
1만 9,000대 발견에서 자동화 공격까지

  - 관리 인터페이스의 인증서 지문과 HTTP 응답 특징으로 장비를 식별함
- 맞춤형 버전 스캐너를 200개 동시 스레드로 실행한 결과, 약 5,000대가 OS 버전 정보에 응답함
  - 미국, 일본, 대만, 한국으로 지역을 좁히고 PHP 8.0.30을 사용하는 신형 분기 중 공격 프로파일과 일치하는 버전을 골라 최종 240대를 선정함
- 자동 배치 도구는 5대씩 병렬 공격하고 대상당 1,800초, 즉 30분의 제한 시간을 적용함
  - PHP2Shell과 Fragnesia 체인을 실행한 뒤 공개 접근 가능한 디렉터리에 103바이트 PHP 루트 웹셸을 설치함

정부 관련 방화벽에서 내부 관리 서버로 이동
- 첫 방화벽에서 추출한 실행 설정에는 CAC(Common Access Card) 인증, 특정 명명 접두사, 표준화된 정부식 자산 이름 등 정부 관련성을 시사하는 특징이 있었음
  - 도메인 컨트롤러, 중앙 방화벽 관리 서버, Keycloak SSO 서버, GitLab 인스턴스, VPN 게이트웨이, AD 도메인 등 전체 내부망 구성이 드러남
- 첫 방화벽은 10월 23일 18:14 UTC 자동 배치에서 침해됐지만, 직후 중단돼 다시 온라인 상태로 돌아오지 않음
  - 약 900MB의 공격 트래픽이 원인이었을 가능성이 있으며, 공격자는 2시간 동안 240회 자동 탐침으로 복구 여부를 확인함
- 인증서 정보로 해당 조직과의 연관성을 확인한 두 번째 방화벽은 원래 배치에서 시간 초과가 발생함
  - 첫 장비의 설정에서 대상의 가치를 파악한 공격자는 별도 작전을 만들고 10월 24일 10:09 UTC에 침해에 성공함
- 이후 8포트 역방향 SSH 터널로 내부망 접근 경로를 구축함
  - 도메인 컨트롤러의 LDAP/LDAPS/RDP, 내부 방화벽 관리 서버, VPN 인프라와 임의 내부망 접근용 SOCKS5 프록시를 연결함
  - systemd 서비스와 rc.local 부팅 훅으로 재부팅 후에도 유지되고 자동 재연결되도록 구성함
- 11:35 UTC, 두 번째 방화벽 침해 후 90분이 지나기 전에 같은 공격 체인으로 터널 안쪽의 중앙 방화벽 관리 서버까지 장악함
  - 이 서버는 조직의 모든 방화벽을 중앙 관리하므로, 관리 대상 장비 전체의 설정, 자격 증명, 네트워크 설정에 접근할 수 있게 됨
  - 이로써 침해한 서버 수는 총 25대가 됨
Active Directory 공격과 확인되지 않은 결과
- 관리 서버는 VPN 사용자 인증을 위해 AD와 LDAP로 연결돼 있어, 공격자는 이를 도메인 공격의 거점으로 사용함
- 루트 권한으로 장비의 마스터 키를 확보해 설정에 암호화돼 있던 LDAP 서비스 계정 비밀번호를 평문으로 복호화하고, 후속 스크립트마다 하드코딩함
  - LDAP 질의로 도메인의 전체 사용자와 그룹을 열거한 사실도 확인됨
- 이후 여러 계정 및 인증 공격을 시도함
  - 조직과 관련된 비밀번호를 모든 사용자 계정에 살포함. 도메인은 lockoutThreshold=0 으로 계정 잠금이 없어 시도 횟수 제한이 없었음
  - 모든 OU에서 백도어 사용자 계정 생성을 시도하고, 기본 MachineAccountQuota 설정을 이용한 컴퓨터 계정 생성도 시도함
  - AD ACL 연결 관계를 분석해 권한 상승 경로를 찾음
  - Keycloak IdP 설정에서 SAML 서명 키 추출을 시도하고, Keycloak SSO의 인증 우회 가능성을 탐색함
