### MCP는 처음부터 잘못된 아이디어였다 | GeekNews

(https://news.hada.io/topic?id=34059)

- 코드를 실행하고 API를 직접 호출할 수 있는 에이전트에는 기존 API를 다시 감싼 MCP 서버가 불필요해졌으며, 필요한 기능이 이미 있는 HTTP API와 CLI를 직접 사용하면 됨
- MCP 서버를 늘릴수록 도구 설명과 스키마가 컨텍스트를 과도하게 차지하고, 이를 해결하기 위한 도구 검색과 서버 관리 시스템까지 추가되는 구조임
- 최신 모델은 처음 접하는 API의 사용법을 파악하고, --help 로 CLI를 탐색하며, 여러 서비스를 스크립트로 묶어 실행할 수 있음
- CLI의 장황한 JSON/XML 응답도 토큰을 낭비하지만, 별도 프로토콜 대신 기존 HTTP의 콘텐츠 협상과 인증 체계를 활용해 개선할 수 있음
- Accept: text/markdown 으로 문서를 받거나 선호하는 프로그래밍 언어에 맞는 예제를 요청하는 등, 에이전트가 필요한 정보를 직접 요청하도록 기존 웹 인터페이스를 다듬는 방향을 제시함
MCP의 등장과 확산
- MCP는 Anthropic이 2024년 11월 25일 공개한 프로토콜로, 에이전트를 외부 서비스와 데이터 소스에 연결하도록 설계됨
  - 당시 모델은 현재보다 능력이 제한적이었고, Claude Code도 없었으며 범용 에이전트 워크플로의 신뢰성도 훨씬 낮았음
  - 외부 서비스 접근으로 새로운 수준의 생산성을 경험하면서 MCP 도입이 급증했고, 경제 전반의 LLM 도입 확대와 맞물림
- Anthropic 주도로 발전한 뒤, 2025년 12월 9일 Linux Foundation 산하 Agentic AI Foundation에 기부됨
- 하루 종일 열린 MCP 행사에서 발표자들은 열정을 보였지만, 모델의 발전으로 이미 MCP가 전제한 시대를 벗어났다는 불만이 이 비판의 출발점임
컨텍스트 비대화와 이를 관리하는 생태계
- 여러 MCP 서버를 추가하면 각 서버의 도구와 스키마가 모델 컨텍스트를 과도하게 차지함
- 하네스 개발자들은 이를 줄이기 위해 범용 검색/실행 패턴 등을 도입함
  - Composio, MintMCP, Pipedream은 외부 서비스의 인증 정보를 한곳에서 관리하고, 에이전트에는 최소한의 도구만 제공하는 방식을 채택함
  - 이런 접근은 단기적으로 유용하지만, 모델 자체의 능력 향상을 충분히 반영하지 못함
- MCP 주변에는 서버 모니터링과 응답 품질 관리뿐 아니라 도구 접근성, 스키마 파악, 적절한 시점의 도구 선택을 지원하는 시스템까지 구축됨
모델의 발전으로 달라진 도구 사용
- 최신 모델은 컴퓨터에서 코드를 실행하고 큰 코드베이스를 추론하며, 이전보다 훨씬 자율적으로 작업할 수 있음
  - 코딩을 위해 스크립트를 작성하고 실행하는 능력이 발전하면서 API 직접 호출에도 능숙해짐
  - 사용자 개입을 최소화한 채 여러 서비스를 조합하고, 처음 접하는 API로도 유용한 워크플로를 만들 수 있음
- Cloudflare의 Code Mode는 LLM이 여러 MCP 호출을 스크립트로 조합하고 샌드박스에서 실행하도록 함
- 모델은 --help 명령으로 CLI 사용법을 탐색할 수도 있음
  - 문서화된 API나 CLI로 접근 가능한 많은 서비스에는 MCP 서버가 더 이상 필요하지 않음
  - 원격 서비스용 MCP 서버 대부분은 결국 이미 존재하는 API를 감싸는 구조임
대부분의 MCP 서버를 HTTP API와 CLI로 대체
- 터미널 접근 권한이 있는 에이전트는 대부분의 MCP 서버를 대체할 수 있고, 더 많은 일을 수행하는 경우도 있음. 이를 근거로 대부분의 MCP 서버를 제거하자고 제안함
- 다만 CLI가 반환하는 JSON/XML 같은 기계 판독용 응답은 장황하고 토큰 소비가 크다는 문제가 남아 있음
- 대안의 상당 부분은 이미 존재함. 문서화된 HTTP API, 표준 콘텐츠 협상, 성숙한 인증 방식을 활용할 수 있음
- 에이전트가 HTTP API를 직접 사용하는 방식을 표준화할 필요가 있음
  - 예를 들어 클라이언트가 에이전트임을 나타내는 헤더를 보내면, 서버가 HTML이나 장황한 JSON 대신 Markdown 또는 텍스트를 반환하도록 할 수 있음
헤더를 활용한 실제 사례
- Accept: text/markdown 을 지원하는 LLM 친화적 서버가 늘고 있으며, 특히 문서 사이트처럼 텍스트 중심인 사이트에서 활용됨
  - 일반적인 HTML 응답 대신 렌더링된 Markdown 파일을 보낼 수 있음
  - 미디어 타입 자체는 표준화되어 있고, 에이전트용 콘텐츠 협상에 활용하는 사례가 늘어남
- Accept-Language 를 활용해 클라이언트가 선호하는 프로그래밍 언어를 전달하는 방식도 있음
  - Vercel 엔지니어는 하네스가 선호 언어를 보내 문서 사이트가 더 구체적인 예제를 제공하도록 제안함
  - 예를 들어 Python을 전달하면 일반적인 문서 대신 Python SDK 문서를 우선할 수 있음
  - Shopify의 Tobi Lutke가 지원 의사를 밝혔으며, 현재 Shopify 문서에 적용됨
기존 공통 프로토콜로 돌아가기
- 인터넷은 공통 프로토콜의 표준화를 통해 성장했으며, 이제 에이전트도 스크립트를 작성하고 필요한 것을 구체적으로 요청할 만큼 발전함
- MCP를 계속 확장하기보다 사용을 종료하고, 이미 필요한 인터페이스를 제공하는 곳에서는 HTTP API와 CLI를 직접 사용하자고 제안함

## 텔레그램 수집 시 유의사항

- 이 컬렉터는 Telethon(MTProto)을 통해 사용자가 실제로 접근 권한을 가진 채널의 메시지를 수집하며, 공개 웹 미리보기(t.me/s/{channel})와 달리 인증된 사용자 세션이 필요하다.
- 한 번에 최대 200개 메시지만 조회하며, 그 이상의 과거 히스토리는 이 단계에서 수집하지 않는다.
- 이미지, 동영상 등 미디어 전용 메시지(텍스트 없음)는 캡처하지 않는다.
- 메시지에 포함된 기사 링크(최대 메시지당 3개, 유튜브/X/인스타그램/페이스북 제외)는 본문을 함께 가져와 아래 '첨부 기사 원문'에 붙인다 - 실패하면 그 링크만 오류로 표시된다.
