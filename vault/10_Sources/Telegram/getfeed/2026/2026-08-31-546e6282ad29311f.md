### The Agentic Awakening - 코딩이 10배 빨라져도 조직 생산성이 따라오지  | GeekNews

(https://news.hada.io/topic?id=33058)

- AI로 개인의 코딩 속도는 10배 이상 빨라질 수 있지만, 기존의 기획, 검토, 승인, 배포 절차가 속도를 흡수해 조직 전체 생산성 향상은 25~30% 수준에 머물 수 있음
- Part I은 여러 에이전트가 장시간 병렬로 일할 수 있는 개발 환경, 전담 AI Ops 조직, 결과 중심의 측정 체계, 보안과 규정 준수를 기술적 토대로 제시함
- Part II는 도구를 나눠주는 것만으로는 전환이 일어나지 않으며, 리더가 직접 에이전트 기반 개발을 익히고 구성원의 저항이 환경 때문인지 정체성 때문인지 구분해야 한다고 주장함
- Part III은 코드 생산 이후의 요구사항 작성, 리뷰, 의사결정, 조직 계층이 새로운 병목이 되므로 1~5명 규모의 자율적인 팀과 짧은 계획 주기로 조직을 다시 설계해야 한다고 설명함
- 에이전틱 전환은 AI가 작성한 코드의 비율을 높이는 작업이 아니라 인프라, 사람, 조직 운영 방식을 함께 바꿔 아이디어가 실제 가치로 배포되는 시간을 줄이는 과정임
20개 이상 기업에서 찾은 공통 문제
- 2026년 상반기 Ramp, Lemonade, Wonderful, DriveNets를 비롯한 20개 이상 기업의 CTO와 엔지니어링 리더를 인터뷰함
- AI 네이티브 스타트업부터 오래된 코드베이스를 가진 후기 단계 기업까지 서로 다른 조직을 살펴봄
- 조사한 선도 기업에서는 AI가 코드의 85~90% 를 작성하고 개인의 코드 생산량이 10배 이상 늘어난 사례도 있었음
- 하지만 실제 조직의 종단 간 생산성 향상은 대체로 25~30% 였고, 가장 앞선 기업에서도 50%를 넘지 못했다고 보고함
- DX가 400개 기업을 분석한 자료에서도 AI 도입률은 65% 증가했지만, Pull Request 처리량의 중앙값은 7.76% 증가하는 데 그침
- 코드를 만드는 시간이 줄어들어도 다음 단계는 그대로 남아 있기 때문임
  - 무엇을 만들지 결정하는 요구사항 작성
  - 제품과 엔지니어링 사이의 전달
  - 코드와 보안 검토
  - 승인과 배포
  - 여러 팀 사이의 의존성과 조율
- 따라서 AI 코딩 도구의 도입률이나 생성된 코드량만으로는 에이전틱 전환을 판단할 수 없음
Part I, 에이전트가 일할 기반 만들기
- 에이전틱 엔지니어링의 성숙도를 네 영역으로 구분함
  - 코딩 인프라: 에이전트가 코드를 작성하고 검증하며 병렬로 작업할 수 있는 환경
  - AI Ops: 모델, 하네스, 컨텍스트, 샌드박스와 비용을 관리하는 전담 기능
  - 측정: 사용량이 아니라 검증되고 배포된 결과를 추적하는 체계
  - 보안과 규정 준수: 에이전트의 코드와 행동, 외부 공격, 모델 공급자를 함께 통제하는 구조
- 코딩 인프라의 발전 단계를 다음과 같이 봄
  - AI가 사람의 입력을 보조하는 Assistant
  - AI가 코드와 설계를 검토하는 Reviewer
  - 하나의 작업을 맡아 구현과 검증을 수행하는 Engineer
  - 여러 에이전트가 장시간 병렬로 작업하는 Team, 이른바 다크 팩토리
- 마지막 단계에서는 개발자가 모든 코드 변경을 직접 지켜보지 않고, 목표와 제약을 정한 뒤 에이전트가 계획, 구현, 테스트, 수정하도록 맡김
- 이를 위해서는 에이전트마다 격리된 작업 공간과 상태, 테스트 환경, 권한 체계가 필요함
- 단순히 모델 API를 연결하는 것보다 작업을 오래 유지하고 실패에서 복구하며 여러 에이전트를 조율하는 하네스가 중요해짐
AI Ops를 부수 업무가 아닌 전담 기능으로
- 선도 기업들은 모델과 에이전트 도구의 운영을 개별 개발자에게 맡기지 않고 2~5명 규모의 AI Ops 팀을 두고 있었음
- AI Ops가 맡는 범위
  - 모델과 에이전트 하네스 평가
  - 프로젝트 컨텍스트와 메모리 관리
  - 샌드박스와 실행 권한 설계
  - 비용과 사용량 추적
  - 공통 프롬프트, 규칙, 평가 기준 관리
  - 새로운 도구를 검증한 뒤 조직 전체에 배포
- 여러 팀이 각자 도구를 고르면 모델, 권한, 메모리, 보안 정책이 분산되고 조직의 학습도 축적되지 않음
- 모델과 범용 도구는 구매하되, 회사의 코드베이스와 업무 방식이 담긴 컨텍스트, 샌드박스, 평가 체계는 직접 소유하는 방식을 권장함
- AI Ops는 중앙에서 모든 작업을 승인하는 조직이 아니라, 각 팀이 안전하게 빠르게 움직일 수 있도록 공통 기반을 만드는 역할임
토큰과 코드량이 아니라 검증된 결과 측정하기
- AI 도구 사용량은 도입 여부를 확인하는 최소 지표일 뿐, 생산성을 나타내지는 않음
- 인터뷰한 고도화된 조직에서는 엔지니어 한 명당 월평균 1,000~2,000달러를 AI 도구에 지출하는 사례가 일반적이었음
- 한 기업은 월평균 1만2,000달러, 일부 개인은 2만8,000달러까지 사용했지만 비용보다 결과를 기준으로 판단함
- 평균 사용량만 보면 조직 내부의 격차를 놓칠 수 있음
  - 한 사례에서는 상위 사용자의 AI 작성 코드량이 중앙값보다 46배 많았음
  - 사용량 분포의 지니계수는 0.77로, 소수의 적극적인 사용자가 대부분을 차지함
- 코드 줄 수는 복잡성이나 가치, 품질을 반영하지 못하므로 다음 지표를 함께 봐야 함
  - 생성된 코드 중 실제로 채택된 비율
  - 채택된 뒤 되돌려진 변경과 회귀 오류
  - 보안 문제와 운영 장애
  - 기능이 요구사항에서 배포까지 도달하는 시간
  - 같은 비용으로 해결한 작업의 복잡도
- 궁극적인 목표는 달러당 생성 코드량이 아니라 달러당 검증되고 배포된 가치임
에이전트 보안은 네 방향에서 다뤄야 함
- 에이전트 보안을 네 가지 문제로 구분함
  - 에이전트가 작성하는 것: 취약한 코드와 의존성, 노출된 시크릿
  - 에이전트가 수행하는 것: 파일 삭제, 외부 전송, 인프라 변경처럼 실행 중 발생하는 위험
  - 공격자가 에이전트에 하는 것: 프롬프트 인젝션과 오염된 외부 콘텐츠
  - 모델과 공급자가 하는 것: 데이터 보관, 학습 사용, 지역과 규제 문제
- 생성된 코드는 SAST, DAST, 의존성 검사, 시크릿 탐지와 같은 기존 보안 파이프라인을 통과해야 함
- 하나의 에이전트가 작성과 검증을 모두 맡기보다 작성자와 비평자 역할을 분리해 서로 다른 모델이나 컨텍스트로 검토할 수 있음
- 외부 문서와 웹 콘텐츠는 신뢰하지 않는 입력으로 격리하고, 에이전트가 사용할 수 있는 도구와 데이터 범위를 최소화해야 함
- 배포, 결제, 고객 데이터 접근처럼 권한이 큰 작업에는 별도의 신원과 짧은 수명의 자격 증명, 사람의 승인을 적용함
- 메모리와 에이전트 간 인계 데이터에도 출처와 권한 정보를 붙여, 한 작업에서 들어온 오염된 지시가 다른 작업으로 퍼지지 않게 해야 함
- 사람의 검토를 모든 코드 줄에 강제하기보다 작업의 위험도에 따라 승인 수준을 다르게 적용하는 방식을 제안함
Part II, 도구가 아니라 사람을 전환시키기
- 에이전틱 전환은 개발자에게 새 도구를 제공하는 것만으로 일어나지 않음
- CEO, CTO, 엔지니어링 리더가 직접 에이전트 기반 개발을 경험하고, 무엇이 달라지는지 이해해야 조직 구조와 평가 방식을 바꿀 수 있음
- 아래에서 자발적으로 시작한 실험은 기존 일정과 평가, 승인 절차를 만나면 원래 방식으로 돌아가기 쉬움
- 구성원을 네 집단으로 구분해 서로 다른 접근이 필요하다고 봄
  - Believers: 여러 에이전트를 병렬로 운영하며 업무 방식을 이미 바꾼 사람
  - Tool Users: 보조 도구로는 사용하지만 기존 개발 방식은 유지하는 사람
  - Legacy Guardians: 오래된 시스템이나 특정 영역의 지식을 지키며 전환에 신중한 사람
  - Resistant: 기술적 근거 없이 기존 방식만 고수하는 사람
- 코드량과 에이전트 수는 집단을 발견하기 위한 신호일 뿐, 개인의 생산성을 단독으로 평가하는 기준으로 사용해서는 안 됨
- 적극적인 사용자는 보호하고 플레이북을 만들게 하며, 일반 사용자는 교육과 실제 업무 실험으로 전환을 돕는 방식이 필요함
시스템의 한계와 사람의 저항을 구분하기
- 에이전트 활용이 낮다고 해서 곧바로 개인의 태도 문제로 판단해서는 안 됨
- 오래된 코드베이스에 테스트, 관측성, 명확한 모듈 경계가 없다면 에이전트도 안전하게 변경할 수 없음
- 이런 architecture-bound 문제는 사람을 교육하기 전에 시스템을 고쳐야 함
  - 시스템 구조와 위험 영역을 먼저 지도화
  - 테스트와 검증 계층 추가
  - 사용자 화면과 내부 시스템을 분리
  - 변경 가능한 모듈 경계 재설계
  - 기존 시스템을 조금씩 대체하는 strangler 방식 적용
  - 기존 결과를 정답으로 삼아 제한된 범위부터 재작성
  - 새 구현을 실제 트래픽에 그림자 실행해 결과 비교
- 반대로 기술적으로 가능하지만 기존 전문성, 지위, 통제력을 잃을까 봐 거부하는 identity-bound 저항도 있음
- 이 경우 기존 전문가의 지식을 에이전트가 따라야 할 검증 기준과 테스트로 전환해야 함
- 작은 기능을 나란히 구현해 비교하거나, 상징적인 낡은 모듈 하나를 에이전트와 함께 재작성하는 방식으로 실제 차이를 보여줄 수 있음
- 충분한 교육과 전환 기회를 주되, 조직의 새로운 기본 방식을 무기한 거부하는 상태까지 허용할 수는 없다고 주장함
엔지니어의 새 일은 오케스트레이션과 검증
- 에이전틱 엔지니어는 코드를 한 줄씩 작성하는 사람보다 여러 작업을 설계하고 위임하며 결과를 검증하는 사람에 가까워짐
- 숙련된 사용자는 동시에 3~5개의 에이전트 작업을 운영하지만, 병렬 작업이 늘수록 컨텍스트 전환과 검토 부담도 커짐
- 운영 가능한 최대치보다 하나 적은 수의 작업을 유지하는 것이 안정적이라는 경험칙을 제시함
- 에이전트의 자율성은 모델 성능보다 결과를 얼마나 자동으로 검증할 수 있는지에 의해 제한됨
  - 테스트
  - 타입 검사
  - 정적 분석
  - 평가 세트
  - 그림자 실행
  - 운영 관측성
- 검증 체계 없이 자연어로 코드를 만들고 바로 받아들이는 것은 바이브 코딩에 가까움
- 에이전틱 엔지니어링에서는 설계, 아키텍처, 품질 기준과 최종 판단이 여전히 사람에게 남음
- 프로젝트의 규칙, 테스트, 스크립트, 문서와 실패 기록을 지속적으로 축적하면 에이전트가 매번 처음부터 배우지 않아도 됨
- 초기에는 이 기반을 만드는 시간이 들지만, 이후 작업마다 지식이 누적되어 속도와 신뢰성이 함께 높아짐
제품도 사람 대신 에이전트를 중심으로 설계하기
- 기존 SaaS의 기능 상당수는 범용 에이전트가 호출하는 도구나 스킬로 흡수될 수 있음
- 제품을 다시 설계할 때 세 단계를 제시함
  - 기존 화면과 기능을 유지하면서 에이전트를 보조 인터페이스로 추가
  - 에이전트가 분석과 의사결정의 중심이 되고 기존 UI는 결과 확인에 사용
  - 전체 제품 경험을 에이전트가 주도하고 사용자는 목표와 승인만 제공
- 기능이 얇은 SaaS는 독립 제품으로 남기보다 범용 에이전트 플랫폼의 한 기능이 될 가능성이 있음
- 기존 매출을 보호하기 위해 전환을 미루면 경쟁자가 먼저 같은 기능을 에이전트 중심으로 재구성할 수 있음
- 현재 제품을 스스로 대체할 가능성이 있더라도, 외부 경쟁자보다 먼저 실험해야 한다고 주장함
Part III, 코드는 빨라졌지만 조직은 그대로
- 에이전트가 코드 작성을 가속하면 기존 조직의 대기 시간이 더 선명하게 드러남
- 대표적인 병목
  - 제품 검토를 기다리는 시간
  - PM이 요구사항을 엔지니어에게 전달하는 과정
  - 코드와 보안 리뷰 대기열
  - 몇 달 단위의 계획과 예산 승인
  - 상태 보고 회의
  - 여러 팀으로 나뉜 소유권
- 기존 절차가 위험을 막기 위한 것인지, 단순히 과거의 작업 속도에 맞춰 생긴 것인지 구분해야 함
- 자동 테스트와 정책 검사로 대체할 수 있는 승인은 제거하고, 위험이 낮은 변경에는 빠른 경로를 열어야 함
- 기술적인 절차를 줄여도 구성원이 계속 허락을 기다린다면 속도는 바뀌지 않으므로, 의사결정 권한도 함께 내려보내야 함
요구사항이 새로운 병목이 되면서 PM 역할도 달라짐
- 구현 시간이 크게 줄어들면 무엇을 만들지 정확히 정의하는 능력이 희소해짐
- 기존에는 PM 한 명이 엔지니어 6~10명을 지원하는 구조가 일반적이었지만, 에이전트 도입 이후에는 두 방향이 나타남
  - 고객과 문제를 이해하는 엔지니어가 제품 판단까지 맡아 PM 의존도를 낮춤
  - 빠르게 구현하는 엔지니어에게 충분한 요구사항을 공급하기 위해 PM과 거의 1대1로 협업
- 문서만 넘기는 대신 PM과 디자이너가 에이전트로 작동하는 프로토타입이나 초기 Pull Request를 만들어 전달할 수 있음
- 엔지니어링은 아키텍처, 품질, 보안과 운영 승인에 집중함
- 몇 달짜리 로드맵보다 짧은 주기로 가설을 구현하고 실제 반응을 확인한 뒤 다음 계획을 정하는 방식이 적합해짐
- 실패 비용이 낮아지면서 더 많은 실험이 가능하지만, 동시에 가치가 불분명한 기능을 대량 생산할 위험도 커짐
1~5명 규모의 자율적인 팀
- 선도 기업에서는 기능 조직을 크게 나누기보다 1~5명 규모의 작은 팀에 문제 전체를 맡기는 방식이 나타남
- 가장 흔한 규모는 2~3명이며, 한 명으로 구성된 팀이 가능한지는 기업마다 의견이 갈림
- 작은 팀은 제품, 설계, 구현, 검증을 한 덩어리로 다루고 외부 승인을 기다리는 시간을 줄임
- 인원이 적다는 것만으로 자율성이 생기지는 않으며 다음 조건이 필요함
  - 고객과 사업 문제에 대한 이해
  - 에이전트를 다루는 능력
  - 품질과 운영 결과에 대한 책임
  - 다른 팀과 충돌하지 않는 기술적 경계
- 주니어 엔지니어가 불필요해진다는 단순한 결론보다는, AI 활용 능력과 제품 감각을 갖춘 사람이 더 빠르게 넓은 역할을 맡을 수 있다는 해석에 가까움
- 반대로 복잡한 시스템에서 쌓은 경험과 판단력은 에이전트의 결과를 검증하고 경계를 설계하는 데 더 중요해질 수 있음
자율적인 팀을 연결하는 네 명의 Chief
- 작은 팀이 각자 빠르게 움직이면 데이터베이스, 인증, API, UI, 테스트 방식이 서로 달라질 위험이 있음
- 이를 막기 위해 회사 전체의 일관성을 책임지는 네 가지 역할을 제안함
  - Chief Architect: 기술 구조와 공통 플랫폼, 시스템 경계
  - Chief Product Officer: 제품 방향과 고객 가치, 팀 간 우선순위
  - Chief Designer: 사용자 경험과 제품 전체의 시각적 일관성
  - Chief Security Officer: 권한, 데이터와 보안 정책
- 이들은 모든 작업을 승인하는 중앙 대기열이 아니라, 여러 팀의 계획과 결과를 에이전트로 지속적으로 살펴보는 역할임
- 각 팀의 일상적인 결정보다 회사 전체에 영향을 주는 선택에만 개입함
- 가장 숙련된 에이전트 사용자가 이 역할을 맡아 여러 프로젝트의 코드와 문서, 의존성, 고객 약속을 함께 분석해야 함
- 조직의 공통 원칙과 과거 결정도 검색 가능한 회사 메모리로 축적해 작은 팀이 같은 판단을 반복하지 않게 해야 함
조직도는 짧고 넓어짐
- AI가 상태 보고, 회의 정리, 진행 상황 수집과 일부 조율을 자동화하면 중간 관리 계층의 역할도 달라짐
- 일부 기업은 관리자 수를 60% 줄이고, 남은 관리자가 기존 4~6명 대신 15~25명을 지원하는 구조를 실험함
- 모든 조직에 동일하게 적용할 수 있는 수치는 아니지만, 관리자의 역할이 작업 배정과 정보 전달에서 다음 방향으로 이동함
  - 팀이 해결할 문제와 경계 설정
  - 인재와 자원 배치
  - 장애물 제거
  - 판단 품질과 결과 책임
- 정보가 여러 관리 단계를 거치지 않으므로 현장과 경영진 사이의 거리가 짧아짐
- 조직도는 계층이 낮아지고 한 관리자가 지원하는 범위가 넓어지는 형태로 변할 수 있음
소프트웨어 구축 능력이 전사로 퍼짐
- 에이전트가 코드 작성과 배포의 진입 장벽을 낮추면서 영업, 재무, 고객 지원과 운영 조직도 직접 내부 도구를 만들 수 있음
- 도메인 전문가와 AI 활용에 능숙한 엔지니어가 짧은 기간 동안 함께 일하는 팀을 구성할 수 있음
- 외부 팀이 요구사항을 받아 대신 만들어주는 방식보다, 실제 업무 담당자가 옆에서 함께 만드는 방식이 효과적임
- 한 사례에서는 자본 배분 작업이 15시간에서 30분으로, 보고서 작성은 이틀에서 10분으로 줄었다고 보고함
- 에이전트가 CRM, 이메일, 결제, 고객 지원 시스템을 오가며 작업할 수 있게 되면 일부 내부 SaaS와 수작업 절차를 대체할 수 있음
- 다만 각 부서가 제각각 소프트웨어를 만들면 보안과 데이터, 중복 시스템 문제가 생기므로 전사 AI Ops와 공통 플랫폼이 필요함
에이전틱 전환을 판단하는 기준
- 세 부분은 순차적인 단계라기보다 함께 발전해야 하는 축임
  - 인프라가 없으면 사람은 에이전트를 신뢰할 수 없음
  - 사람이 바뀌지 않으면 좋은 인프라도 사용되지 않음
  - 조직이 바뀌지 않으면 빨라진 개발 속도가 승인과 전달 과정에서 사라짐
- AI가 작성한 코드 비율이나 도구 사용량만 높이는 것은 전환의 결과가 아님
- 요구사항에서 검증과 배포까지 걸리는 시간, 품질, 운영 안정성, 비용 대비 가치가 함께 개선되어야 함
- 핵심은 사람을 코드 작성에서 완전히 제거하는 것이 아니라, 사람이 문제 정의, 판단, 설계와 검증에 더 많은 시간을 쓰게 만드는 것임
- 2026년 7월 시점의 기업 인터뷰와 사례를 바탕으로 만든 실전 플레이북이며, 빠르게 변하는 모델과 가격, 도구 관련 수치는 시점에 따라 달라질 수 있음

## 텔레그램 수집 시 유의사항

- 이 컬렉터는 공개 웹 미리보기(t.me/s/{channel})만 수집하며, 비공개 채널 수집은 이 단계에서 구현하지 않는다.
- 웹 미리보기는 페이지당 최대 20개 메시지씩, 최대 10페이지(최근 약 200개)까지만 페이지네이션한다.
- 이미지, 동영상 등 미디어 전용 메시지(텍스트 없음)는 캡처하지 않는다.
- 메시지에 포함된 기사 링크(최대 메시지당 3개, 유튜브/X/인스타그램/페이스북 제외)는 본문을 함께 가져와 아래 '첨부 기사 원문'에 붙인다 - 실패하면 그 링크만 오류로 표시된다.
