### AI 시대에 코드 리뷰에서 살아남는 방법은? | GeekNews

(https://news.hada.io/topic?id=33244)

- 동료들이 AI를 적극 활용하면서 리뷰할 PR이 평균 약 6,000줄의 diff로 커졌고, 효과적인 검토가 어려운 상황임
- 사람이 구축 중인 시스템의 작동 방식을 이해해야 한다는 생각 때문에 일반적인 질의응답 외에는 AI 리뷰 활용을 주저하며, AI의 설명도 장황하고 이해하기 어렵다고 느낌
- 이런 대규모 PR에 대응하는 데 도움이 된 조직적·개인적 전략을 찾고 있음
Lobsters 답변 종합
- 원글의 토론에서는 큰 PR을 나누고 작성자의 설명 책임을 강화하자는 의견이 반복됨
- 다만 이를 실행하려면 팀과 관리자가 코드 리뷰의 목적과 기준에 합의해야 하며, 리뷰어 개인의 노력이나 AI 도구만으로 해결하기 어렵다는 지적도 많음
- 
검토할 수 있는 크기로 나누기
  - AI로 작성한 코드에도 사람이 작성한 코드와 같은 리뷰 기준을 적용해야 함
  - 한 팀은 코드 이동 같은 예외를 제외하고 PR 변경분을 400줄 이하로 제한함
  - 줄 수와 복잡도의 관계는 언어마다 다르지만, 6,000줄짜리 변경을 한 번에 읽고 이해하기는 어려움
  - 큰 변경은 기능이나 목적별로 나눠 연속 PR(stacked PR) 이나 커밋으로 제출할 수 있음
    - AI는 코드 분할과 충돌 해결을 도울 수 있지만, 어디서 나눠야 이해하기 좋은지는 사람이 판단해야 함
    - 완성한 뒤 쪼개려면 손이 많이 가므로 계획 단계부터 검토 단위를 정하는 편이 나음
- 
작성자가 변경의 의도를 설명하기
  - PR에는 왜 필요한지, 무엇을 바꿨는지, 다른 방법을 고려했는지, 왜 작동하는지가 담겨야 함
  - 설명 없이 코드를 넘기면 리뷰어가 구현을 역공학하며 작성자의 의도까지 알아내야 함
  - AI가 작성한 분석을 첨부하더라도, 맨 앞에는 작성자가 직접 이해하고 정리한 의도와 판단 근거가 필요함
  - 작성자는 코드와 결정에 관한 후속 질문에도 답할 수 있어야 함
  - 장황한 설명과 어려운 용어, 코드를 그대로 반복하는 주석을 줄이는 일도 PR 준비에 포함됨
- 
AI로 리뷰 준비를 돕기
  - 사람이 보기 전에 린터, 테스트와 AI 리뷰를 실행해 기본 오류와 테스트 누락을 정리할 수 있음
  - 계획 검토 → 작은 커밋으로 구현 → AI 사전 리뷰와 수정 → 사람의 코드 리뷰 순서로 작업하는 사례가 있음
  - AI에게 변경의 목적, 읽기 시작할 파일, 주의할 부분을 정리한 리뷰 안내서를 만들게 하면 코드 파악에 도움이 됨
  - 사람이 먼저 독립적으로 검토한 뒤 AI의 지적과 비교하는 방식도 가능함
  - 반복되는 리뷰 기준은 AGENTS.md 나 스킬에 넣어 같은 문제가 계속 올라오는 것을 줄일 수 있음
- 
AI 리뷰를 언제 끝낼지도 사람이 판단하기
  - AI 리뷰가 경계 조건이나 놓친 오류를 찾아내더라도, 반복할수록 사소한 취향을 지적하거나 앞선 수정 요구를 뒤집을 수 있음
  - 실제로 첫 리뷰는 유용했지만 두 번째는 흠잡기로 바뀌고, 세 번째에는 이전 요구를 되돌리라고 한 사례가 있음
  - 병합할 만큼 충분히 좋은 코드인지를 판단하는 기준이 없으면, AI는 계속 고칠 거리를 만들어낼 수 있음
  - 리뷰어는 AI의 지적이 실제 문제인지, 수정할 가치가 있는지 걸러야 하며 모든 출력을 작성자에게 그대로 전달해서는 안 됨
  - 도구별 평가는 엇갈리므로 실제 코드베이스에 적용해 피드백의 유용성과 불필요한 지적을 함께 비교할 필요가 있음
- 
거절만 하지 말고 검토받을 방법을 알려주기
  - 큰 PR을 돌려보낼 때는 크기와 설명의 문제를 짚고, 어떻게 나누면 검토할 수 있는지도 함께 알려줌
  - 작은 PR은 빠르게 검토하고 큰 PR에는 필요한 시간과 부담을 명확히 설명함
  - 작성자와 함께 코드를 보며 질문과 우려를 말로 풀어내면 리뷰 기준을 공유하기 쉬움
  - PR 크기, 설명 요건, 작성자의 책임과 승인 기준을 팀 규칙으로 정하면 개인 간의 실랑이를 줄일 수 있음
  - 이슈 작성과 최종 PR 사이에도 설계와 구현 방향을 함께 논의해야, 완성된 코드를 처음 보는 리뷰어에게 이해의 부담이 몰리지 않음
- 
팀이 기대하는 리뷰 수준부터 맞추기
  - 사람이 모든 변경을 읽고 시스템을 이해하는 개발 방식과, AI에 구현을 맡기고 기능과 테스트 중심으로 확인하는 방식은 리뷰에 대한 기대가 다름
  - 같은 팀에서 이 기대가 엇갈리면 한쪽은 검토가 부실하다고 느끼고, 다른 쪽은 리뷰가 진행을 막는다고 느끼게 됨
  - 관리자가 리뷰에 무엇을 기대하고, 리뷰어에게 어떤 책임과 거절 권한을 주는지부터 합의해야 함
  - 속도만 요구하면서 검토할 시간을 주지 않는 조직에서는 리뷰어 개인의 노력이나 도구 추가만으로 문제를 해결하기 어려움
  - 소진을 피하려 직접 요청받은 PR만 검토하거나 업무 범위를 줄인 사례도 있음
  - 검토 방식을 바꾸더라도, 사람이 실제로 읽지 못한 코드를 충분히 검토한 것처럼 취급해서는 안 됨

## 텔레그램 수집 시 유의사항

- 이 컬렉터는 공개 웹 미리보기(t.me/s/{channel})만 수집하며, 비공개 채널 수집은 이 단계에서 구현하지 않는다.
- 웹 미리보기는 페이지당 최대 20개 메시지씩, 최대 10페이지(최근 약 200개)까지만 페이지네이션한다.
- 이미지, 동영상 등 미디어 전용 메시지(텍스트 없음)는 캡처하지 않는다.
- 메시지에 포함된 기사 링크(최대 메시지당 3개, 유튜브/X/인스타그램/페이스북 제외)는 본문을 함께 가져와 아래 '첨부 기사 원문'에 붙인다 - 실패하면 그 링크만 오류로 표시된다.
