### 배치 처리·연산자 융합·SIMD로 Postgres 분석 성능을 300배 높인 pgrust | GeekNews

(https://news.hada.io/topic?id=32264)

- pgrust 0.2는 쿼리 엔진을 중심으로 성능을 개선해 이전 버전보다 10배, OLTP에서 Postgres보다 30%, ClickBench에서 300배 빠르며 ClickHouse도 앞섬
- Postgres의 행 단위 Volcano 실행 모델은 각 행마다 런타임에 결정되는 next() 를 호출해 함수 호출 비용이 크고 CPU 파이프라이닝 같은 최적화를 활용하기 어려움
- 5억 개의 float8 값을 더하는 축소 실험에서 1.3초가 걸린 행 단위 실행을 배치 처리로 480ms, 연산자 융합으로 358ms, SIMD로 135ms까지 단축함
- 스택 버퍼를 사용하는 배치는 할당과 호출 횟수를 줄이고, 연산자 융합은 스캔과 집계를 합쳐 복사를 없애며, SIMD는 여러 값을 동시에 처리함
- 모든 쿼리 조합에 최적화된 융합 코드를 미리 준비할 수 없어 JIT 컴파일이 필요하며, 부동소수점 SIMD는 덧셈 순서가 달라져 결과에 미세한 차이가 생길 수 있음
pgrust 0.2의 성능
- pgrust 0.2는 성능에 집중한 릴리스로, 이전 버전보다 10배 빨라짐
- 작업 유형별 벤치마크 결과는 다음과 같음
  - OLTP 벤치마크에서는 Postgres보다 30% 빠름
  - ClickHouse의 분석 데이터베이스 벤치마크인 ClickBench에서는 Postgres보다 300배 빠르며 ClickHouse도 앞섬
- 전체 300배 향상 가운데 쿼리 엔진 변경만으로 얻은 성능 향상은 약 10배임
Postgres에 최적화 여지가 큰 이유
- Postgres의 기원은 디스크 입출력이 데이터베이스 성능의 주된 병목이던 1980년대까지 거슬러 올라감
- 세 가지 변화로 CPU와 메모리 성능의 중요성이 커짐
  - 많은 데이터셋이 RAM에 들어가면서 디스크 입출력 대부분이 사라짐
  - RAM보다 큰 데이터셋도 분석 작업에서는 데이터를 대량 스캔하므로, 병목이 디스크 처리량보다 CPU나 메모리 처리량에 놓이는 경우가 많음
  - NVMe는 하드디스크보다 수백 배 빨라짐
- 쿼리 엔진은 데이터베이스에서 CPU를 주로 사용하는 부분이므로, pgrust는 같은 쿼리를 처리할 때 Postgres보다 CPU와 메모리 대역폭을 적게 사용하도록 최적화함
5억 개 값 합산 실험
- generate_series 로 만든 5억 개의float8 값을SUM 하는 Postgres 쿼리는 병렬 쿼리를 끈c8g.4xl 환경에서 약 20초 걸림
- 같은 값을 Rust의 단순 for 루프로 합산하면 358ms로 약 55배 빠름
- 두 구현은 완전히 동일한 조건이 아님
  - Postgres 내부에서는 쿼리 엔진 외에도 더 많은 작업이 수행됨
  - 큰 부가 비용에는 잠금, Postgres 저장 형식 파싱과 관련 튜플 추출이 포함됨
- 데이터베이스 최적화는 이런 부가 비용을 가능한 한 제거하는 작업임
Postgres의 Volcano 실행 모델
- Postgres는 SQL을 실행 방법을 나타내는 내부 쿼리 계획(Query Plan) 으로 변환함
  - 예제 계획은 테이블 행을 순차적으로 읽고 값을 합산함
  - 조인, 정렬, 서브쿼리가 들어가면 계획이 복잡해지며 Postgres에는 40개가 넘는 계획 노드 유형이 있음
- 쿼리 엔진은 계획에 따라 행을 가져오고 집계를 수행하며, Postgres는 Volcano 모델을 사용함
- 각 계획 노드는 한 행을 반환하는 next() 메서드를 지원함
  - 순차 스캔의 next() 는 다음 행을 반환함
  - 집계 노드의 next() 는 전체 집계를 계산한 뒤 단일 결과 행을 돌려줌
  - 루트 노드가 더는 행을 반환하지 않을 때까지 next() 를 호출하면 계획 실행이 끝남
- 순차 스캔의 
- 모든 노드에 하나의 메서드만 구현하면 돼 구조가 단순하지만, 축소 구현에서도 실행에 1.3초가 걸려 단순 루프보다 느림
- 벤치마크 코드의 black_box 는 컴파일러 최적화가 측정을 무효화하지 못하게 함
배치 처리로 행 단위 호출 제거
- 가장 큰 비용은 next() 가 한 번에 한 행만 처리해 5억 개 행마다SeqScan.next() 를 호출한다는 점임
- 특히 런타임에 호출 대상이 결정되는 함수는 CPU 파이프라이닝 같은 최적화가 제대로 작동하기 어려움
- next_batch() 가 최대 1,024개 값을 한 번에 전달하도록 바꾸자 실행 시간이 1.3초에서 약 480ms로 줄어듦
- 배치 버퍼는 스택에 할당되므로 집계 노드가 실행 중 메모리를 별도로 할당하지 않음
  - 메모리 할당은 상대적으로 느려 초고속 코드에서는 할당 횟수를 최소화해야 함
연산자 융합으로 복사 제거
- 배치 처리 후 프로파일링에서 값을 버퍼로 복사하는 copy_from_slice 가 병목으로 확인됨
- 함께 수행되는 흔한 연산을 단일 노드로 합치는 연산자 융합(operator fusion) 으로 이 복사를 없앨 수 있음
- SumAggregateSequentialScan 은 순차 스캔과 합산을 하나의 노드로 결합해 테이블을 직접 순회함
- 결과 코드는 단순 for 루프와 사실상 같아져 동일한 358ms 성능을 냄
- 특정 쿼리에 맞춘 융합 노드를 미리 작성하는 방식은 흔한 몇 가지 경우에 유효하지만, 준비하지 않은 조합을 빠르게 만나게 됨
JIT 컴파일의 역할
- JIT 컴파일은 쿼리별로 이상적인 코드를 생성해 미리 준비되지 않은 조합에도 연산자 융합을 적용할 수 있게 함
- pgrust의 JIT 컴파일 활용 방식은 후속 글에서 다룰 예정임
SIMD로 여러 행 동시 처리
- SIMD는 하나의 CPU 연산을 여러 데이터에 동시에 적용해 행을 하나씩 처리하는 방식보다 빠르게 계산함
- AArch64 SIMD로 여러 f64 값을 병렬 합산하자 실행 시간이 135ms로 줄어듦
  - 단순 for 루프보다 거의 3배 빠름
  - 최초 Volcano 구현보다 약 10배 빠른 수준임
- 단순 
- 컴파일러가 루프를 자동으로 SIMD로 바꾸기도 하지만, 이 예제의 부동소수점 합산에는 일반적으로 적용하지 않음
- 부동소수점 연산은 결합법칙이 성립하지 않아 합산 순서를 바꾸면 결과가 미세하게 달라질 수 있음
단계별 결과와 측정 조건
- 세 가지 최적화를 차례로 적용한 결과는 다음과 같음
- 측정 환경은 AWS c8g.4xlarge , Graviton4, 16 vCPU, PostgreSQL 18.4임
- max_parallel_workers_per_gather = 0 으로 병렬 쿼리를 끄고 데이터를 공유 버퍼에 올린 상태에서 측정함
- Postgres 수치는 5회 실행의 중앙값이며, Rust는 cargo build --release 로 빌드해 구현별 4회씩 같은 머신의 단일 프로세스에서 실행함
- 배치 처리, 연산자 융합, SIMD를 포함한 여러 최적화가 pgrust의 분석 쿼리 성능을 Postgres보다 수백 배 높이는 기반이 됨
