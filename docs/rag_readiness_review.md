# 1부. 내 시스템은 어떻게 생겼나

## 한 문장으로 말하면

매일 47군데에서 투자 관련 글을 긁어와 파일로 쌓아두고, 그 글들을 LLM에게 읽혀서
"이게 내가 들고 있는 종목에 좋은 소식인지 나쁜 소식인지"를 정리한 다음, 한국어 일일 리포트를
만들어주는 프로그램입니다. 주문은 절대 넣지 않습니다.

## 규모

| 항목 | 수 |
|---|---:|
| 파이썬 파일 | 170개 |
| 코드 줄 수 | 21,132줄 |
| 테스트 파일 | 136개 |
| 등록된 수집 소스 | 47개 |
| 추적 중인 종목 | 72개 |
| 모아둔 문서 | 4,818건, 26,837,466자 |

테스트가 136개 있다는 것은, 바이브코딩으로 만들었더라도 각 부품이 의도대로 도는지 확인하는
장치는 꽤 촘촘하게 깔려 있다는 뜻입니다.

## 이 프로그램은 네 개의 층으로 되어 있습니다

```
[1층] 모으는 층      인터넷에서 글을 긁어옵니다
   ↓
[2층] 쌓아두는 층    긁어온 글을 마크다운 파일로 저장합니다
   ↓
[4층] 찾는 층        쌓아둔 글 중에서 필요한 것만 골라냅니다   ← 최근에 만들었고, 아직 연결 안 됨
   ↓
[3층] 판단하는 층    LLM에게 읽혀 주장을 뽑고 매수·매도 신호를 만듭니다
```

층 번호가 3, 4 순서로 뒤집혀 있는 것이 이 문서의 핵심입니다.
**원래 있어야 할 자리(2층과 3층 사이)에 4층이 아직 안 들어가 있습니다.**
지금은 2층에서 3층으로 바로 갑니다. 즉 쌓아둔 글을 골라내지 않고 최근 것을 통째로 LLM에 넣습니다.

굵게 표시한 두 폴더가 최근 2일 사이에 새로 생긴 것이고, 이 문서가 주로 다루는 부분입니다.

## 명령어를 하나 치면 무슨 일이 일어나나요

`run-daily` 하나만 치면 아래가 순서대로 돕니다.

```
run-daily
  │
  ├─ 1. collect      47개 소스를 돌면서 새 글을 받아옵니다
  │                  → vault/10_Sources/ 아래에 마크다운 파일로 저장
  │
  ├─ 2. analyze      아직 안 읽은 최근 문서를 골라 Claude에게 통째로 넣습니다
  │                  → 핵심 주장, 근거, 반대 근거를 뽑아 저장
  │
  ├─ 3. portfolio    보유 종목 평가금액과 위험 한도를 계산합니다
  │
  ├─ 4. 포트폴리오 모니터   오늘 뽑은 주장을 보유 종목과 대조해 강세·약세 신호를 만듭니다
  │
  ├─ 5. 텐베거 발굴   10배 후보를 찾아봅니다
  │
  └─ 6. report       위 결과를 모아 한국어 일일 리포트를 만듭니다
```

2번을 잘 보시면 됩니다. **"아직 안 읽은 최근 문서를 골라"** 가 전부입니다.
"질문에 답이 될 만한 문서를 찾아서"가 아닙니다. 여기가 검색이 빠져 있는 자리입니다.

## 데이터는 어디에 사는가

| 위치 | 무엇이 들었나 | 크기 |
|---|---|---|
| `vault/10_Sources/` | 긁어온 원문. 진짜 자료는 전부 여기 있습니다 | 마크다운 4,818개 |
| `vault/40_Analysis/` | 사람이 직접 쓴 분석 메모 | 1개 |
| `vault/50_Reports/` | 만들어진 리포트와 질의응답 기록 | 1개 |
| `vault/20_Knowledge/` | 새로 만든 지식 레이어가 들어갈 자리 | 지금 이 컴퓨터에는 아직 없습니다 |
| `data/index.sqlite3` | 무슨 문서를 모았는지 적은 **목록표**. 본문은 안 들어 있습니다 | 2,538행 |
| `config/*.yaml` | 어디서 뭘 모을지, 어떤 종목을 볼지 정한 설정 | 7개 파일 |
| `config/prompts/*.md` | Claude에게 보낼 질문 문구 10개 | 10개 파일 |

여기서 헷갈리기 쉬운 것이 `data/index.sqlite3`입니다. 이름에 index가 들어 있어서 검색용처럼 보이는데,
실제로는 **"이미 모은 문서 목록"** 입니다. 같은 글을 두 번 저장하지 않으려고 만든 것이고,
본문 글자가 들어 있지 않아서 이걸로는 내용 검색을 할 수 없습니다.

## 문서 하나는 이렇게 생겼습니다

`vault/10_Sources/DART/483650/2025/2025-05-13-1cfd5fc1ac3e40b6.md` 를 열면 이렇습니다.

```markdown
---
id: 1cfd5fc1ac3e40b6
source_type: dart
source_name: '483650'
author: 달바글로벌
title: '[분기보고서] 달바글로벌 분기보고서 (2025.03) (2025-05-13)'
source_url: https://dart.fss.or.kr/...
published_at: '2025-05-13T00:00:00Z'
language: ko
content_capture:
  mode: full
companies: ['483650']
document_type: dart_filing
filing_type: 분기보고서 (2025.03)
llm_processed: false
---

## 원문

달바글로벌 분기보고서 (2025.03) ...
```

위쪽 `---` 로 감싼 부분을 **Metadata**라고 부릅니다. 사람이 읽는 본문이 아니라, 프로그램이
"이게 언제, 어디서, 무슨 종목에 대해 나온 글인지"를 알아보라고 붙여둔 꼬리표입니다.
스터디 3주차에서 말한 OKF(Markdown 본문 + YAML Metadata)가 바로 이 모양입니다.
**이 시스템은 처음부터 OKF 형태로 저장하고 있었습니다.** 의도했든 아니든 맞게 만들어져 있습니다.

## 지금 브랜치 상황

이게 중요합니다. 검색 관련 코드는 **아직 본체에 합쳐져 있지 않습니다.**

| 브랜치 | 최신 커밋 | 검색 코드가 있나 |
|---|---|---|
| `main` (본체) | 2026-08-10 | 없습니다 |
| `feat/vault-search-indexing` | 2026-08-25 | 있습니다. `indexing/` 12개 + `knowledge/` 5개 |

즉 지금 `run-daily`를 실행하면 검색 기능은 하나도 안 돕니다. 실험용 스크립트로 손으로
돌려야만 동작합니다.

# 2부. 스터디 개념으로 보면 지금 어디쯤인가

3주차와 4주차에서 배운 개념을 하나씩 놓고 "이게 지금 있나 없나"를 표시했습니다.

## 3주차 개념

| 개념 | 이게 뭐냐면 | 상태 | 지금 어떤가 |
|---|---|:--:|---|
| OKF | 마크다운 본문 + YAML 꼬리표로 지식을 정리하는 형식 | 있음 | 원문 4,818건이 처음부터 이 모양입니다. 최근에 그 위에 정리된 지식 레이어까지 만들었습니다 |
| 개념 단위 문서 | 문서 하나가 하나의 개념을 담게 정리하는 것 | 있음 | 새로 생겼습니다. 종목 335개, 투자자 5명, 채널 30개를 별도 문서로 만들어 허브로 씁니다 |
| Metadata | 검색 전에 걸러낼 수 있게 붙이는 꼬리표 | 부분 | `status`(쓸 만한지), 기간, 종목이 지식 레이어에 생겼습니다. 다만 `assets` 필드는 여전히 비어 있습니다 |
| Link 관계 | 문서끼리 마크다운 링크로 연결 | 있음 | 링크 14,649개, 깨진 링크 0개. 검증기가 자동으로 확인합니다 |
| Chunking | 긴 문서를 검색하기 좋은 조각으로 자르기 | 있음 | 섹션, 문단, 표 순서로 자릅니다. 표를 자를 때 헤더 줄을 조각마다 다시 붙입니다 |
| Contextual Retrieval | 조각만 보면 문맥을 알 수 없으니 앞에 설명을 붙이는 것 | 부분 | LLM으로 문장을 생성하는 대신, 확정된 꼬리표를 붙였습니다. 원안대로 생성하는 코드도 있지만 아직 안 돌렸습니다 |
| BM25 | 글자가 정확히 일치하는 문서를 찾는 검색 | 있음 | SQLite FTS5로 구현 |
| 한국어 처리 | `삼성전자의`와 `삼성전자`를 같은 말로 보게 하는 것 | 있음 | 한글을 두 글자씩 쪼개 색인합니다 |
| Vector Search | 단어가 안 겹쳐도 뜻이 비슷한 문서를 찾는 검색 | **없음** | 이게 없어서 못 푸는 질문이 있습니다. 3부에서 다룹니다 |
| Hybrid Search | 위 두 검색을 합치는 것 | **없음** | 합칠 상대가 없습니다 |
| Reranker | 찾아온 후보를 다시 한 번 정밀하게 줄 세우는 것 | **없음** | |

## 정리하면

**있는 것**: 자료를 모으고, 정리하고, 조각내고, 꼬리표를 붙이고, 글자로 찾고, 성능을 측정하는 것.
**없는 것**: 뜻으로 찾는 것(Vector), 후보를 다시 줄 세우는 것(Reranker),
그리고 검색을 언제 어떻게 쓸지 LLM이 판단하는 것(Agent).
**있는데 안 쓰는 것**: 검색 계층 전체. `main`에 안 붙어 있습니다.

# 3부. 지금까지 무슨 실험을 했고 뭘 알아냈나

## 3-1. 실험이 무엇이었는지부터

같은 시험지를 놓고 검색기에 처방을 하나씩만 더해가며 점수 변화를 잰 것입니다.
이렇게 한 단계씩 더하거나 빼서 원인을 확인하는 방식을 **ablation**이라고 부릅니다.

```
V0  아무 처방 없음      문서를 통째로 색인하고 띄어쓰기로만 자릅니다 (원래 상태)
V1  + 조각내기          섹션, 문단, 표 단위로 자릅니다
V2  + 한글 두 글자씩    '삼성전자'를 '삼성', '성전', '전자'로 쪼갭니다
V3  + 꼬리표 붙이기      조각 앞에 "출처 dart, 종목 005930, 분기보고서"를 붙입니다
V4  + 본문 없는 문서 제외
V5  + V4에서 제외만 빼기 (무엇이 문제였는지 가리려고 만든 것)
V6  + 어절 통째도 같이 색인
V7  + 정리된 지식 레이어에서 색인하고, 종목·기간으로 미리 거르기   ← 5주차에 추가
```

시험지는 네 종류입니다.

| 시험지 | 문항 수 | 어떻게 만들었나 | 난이도 |
|---|---:|---|---|

## 3-4. 여기서 배울 점

**1. 개선의 대부분은 한국어 처리에서 나왔습니다.**
V0과 V1은 한국어 형태변형 질문 100건에서 정답률이 **정확히 0**입니다.
문서에 `삼성전자의`라고 적혀 있는데 `삼성전자`로 검색하면 원리적으로 못 찾습니다.
띄어쓰기로 자르는 방식에서는 완전히 다른 단어이기 때문입니다. V2에서 0.950으로 올라갑니다.

**2. 조각내기의 효과는 정확도가 아니라 읽어야 할 양에서 나왔습니다.**
정답률은 0.810에서 0.822로 거의 안 움직였는데, 읽어야 할 글자가 19,250자에서 2,749자로 7배 줄었습니다.
긴 문서가 걸리는 질문만 보면 52,093자에서 3,262자로 16배입니다.

**3. 뭔가를 버리는 처리는 질문 유형별로 확인해야 합니다.**
"본문 없는 문서는 쓸모없으니 빼자"는 상식적이었는데, 접수번호로 찾는 질문의 정답률이
0.993에서 0.340으로 무너졌습니다. 접수번호로 찾는 공시가 대부분 본문 없는 문서였기 때문입니다.

**4. 필터를 잘못 걸면 정답을 지웁니다.**
처음 미리 거르기를 켰을 때 자동 평가 정답률이 0.978에서 0.891로 떨어졌습니다.
잃은 55건 중 50건이 **연도를 잘못 뽑은 것**이었습니다. 네 자리 숫자를 전부 연도로 봤더니
금액이나 계좌번호가 연도로 잡혀서, 필터가 정답 문서를 후보에서 지워버린 것입니다.
`년`, `FY`, `Q1` 같은 신호가 있을 때만 연도로 보게 고치자 0.973으로 회복했습니다.

**5. 규칙을 고치는 것이 루프를 도는 것보다 낫습니다.**
같은 문제를 두 가지로 갚아봤습니다. 실패하면 필터를 풀고 다시 찾는 루프를 붙였더니 0.931,
연도 규칙 자체를 고쳤더니 0.973입니다. **에이전트 루프로 덮기 전에 규칙을 고치는 것이 먼저입니다.**

**6. 어휘 기반 검색으로는 넘지 못하는 벽이 있습니다.**
사람이 쓴 24개 질문 중 9개는 질문에 쓴 단어가 정답 문서에 거의 없습니다. 세 건은 아예 하나도 없습니다.

## C. 시험지를 늘립니다

- **할 일**: 사람이 쓴 질문을 최소 100건까지 늘리고 유형별로 나눕니다. 접수번호 조회, 사실 조회, 표현이 다른 질문, 여러 문서를 봐야 하는 질문, 그리고 **답이 없는 질문**까지 포함합니다. 그리고 검색뿐 아니라 답변 품질도 따로 잽니다.
- **왜 임베딩보다 먼저인가**: 이게 이 문서에서 5주차 문서와 순서가 다른 유일한 지점입니다. 5주차 문서는 임베딩을 1순위, 평가셋 확대를 5순위로 두었습니다. 그런데 임베딩이 겨냥하는 대상이 저 9건이고, 9건으로는 좋아졌는지 알 수가 없습니다. 최소한 같이 진행해야 합니다.

## D. Vector Search를 붙이고 두 검색을 합칩니다

- **할 일**: 다국어 임베딩 모델로 조각 47,121개를 벡터로 바꾸고, 기존 글자 검색 결과와 합칩니다(RRF).
- **효과**: 단어가 안 겹치는 8건에 도달할 길이 생깁니다. 다만 이건 추정이고, C를 안 하면 확인이 안 됩니다.
- **비용**: 조각 47,121개에 대해 한 번만 계산하면 되고, 다시 색인할 때만 재계산합니다.

## E. 재검색 루프의 판정을 LLM으로 바꿉니다

- **할 일**: 지금은 "단어가 얼마나 겹치나"로 판정합니다. 이걸 LLM에게 "이 결과가 질문과 관련 있나"를 묻는 방식으로 바꿉니다.
- **왜 나중인가**: 4-3에서 본 것처럼 지금 루프는 이득이 없습니다. Vector Search가 들어와 후보 품질이 올라간 뒤에 붙여야 값어치가 납니다.

## F. Reranker를 붙입니다

- **할 일**: 상위 50~100개 후보를 한 번 더 정밀하게 줄 세웁니다.
- **효과**: 정답률보다 "한 번에 맞히는 비율"이 올라갑니다. 상위 1건만 넣고도 답할 수 있게 되면 읽어야 할 양이 다시 크게 줄어듭니다.
- **왜 마지막인가**: 후보 자체가 나쁘면 다시 줄 세워도 소용이 없습니다.

## 지금 안 해도 되는 것

**본격적인 Agent를 붙이는 일**은 지금이 아닙니다. 4주차 18절이 정리한 대로,
검색 대상이 부실하면 Agent가 똑똑해도 결과가 좋아지지 않습니다.
코퍼스의 32%에 본문이 없는 상태에서 Agent를 먼저 붙이면 없는 근거를 찾느라 루프만 돌게 됩니다.
6주차에 Agent를 다룬다면, 그 전에 A와 B는 정리돼 있는 편이 좋겠습니다.

# 6부. 스터디에서 같이 이야기해볼 것

1. **V4에서 무슨 일이 있었나요.** "본문 없는 문서는 검색에서 빼자"는 판단이 왜 상식적으로 옳아 보였고, 왜 틀렸을까요. 우리 팀 데이터에도 "당연히 버려도 되는 것"이 있다면 무엇인가요.

2. **연도 오탐 사건.** 네 자리 숫자를 연도로 봤다가 정답 50건이 사라졌습니다. 필터는 후보를 좁혀서 좋아지게 하는 장치인데, 동시에 정답을 지울 수도 있습니다. 이 위험을 어떻게 미리 잡을 수 있을까요.

3. **규칙 vs 루프.** 같은 문제를 규칙 수정으로 고치면 0.973, 에이전트 루프로 덮으면 0.931이었습니다. 그리고 규칙을 고친 뒤에는 루프가 이득이 없습니다. 그럼 루프는 언제 값어치가 날까요.

4. **표본 24건 문제.** 사람이 쓴 평가 질문을 100건까지 늘리는 비용과 그로 얻는 것을 비교하면 어디까지가 적당할까요.

5. **순서에 대한 이견.** 5주차 문서는 임베딩을 1순위, 평가셋 확대를 5순위로 두었습니다. 이 문서는 평가셋을 임베딩보다 앞에 두자고 제안합니다. 어느 쪽이 맞을까요.

6. **만든 것이 안 붙어 있는 문제.** 검색 계층은 잘 만들어졌지만 `main`에 없습니다. "실험으로 검증한 다음 붙인다"는 순서는 맞는데, 붙이는 단계에서 잊히는 경우가 많습니다. 무엇을 미리 정해두면 막을 수 있을까요.

# 부록: 용어 30초 사전

| 용어 | 30초 설명 |
|---|---|
| **RAG** | 질문을 받으면 관련 자료를 먼저 찾아서, 그 자료를 근거로 LLM이 답하게 하는 구조입니다. 특정 제품이 아니라 설계 방식입니다 |
| **Vault** | 모아둔 원문 마크다운 파일이 사는 폴더입니다. Obsidian이라는 메모 앱으로 열어볼 수 있는 형태입니다 |
| **Metadata** | 문서 맨 위에 붙는 꼬리표입니다. 제목, 날짜, 종목, 출처처럼 프로그램이 알아보기 위한 정보입니다 |
| **OKF** | 마크다운 본문 + YAML 꼬리표 + 마크다운 링크 + 폴더 구조로 지식을 정리하는 형식입니다. 검색 엔진이나 DB가 아니라 표기 규약입니다 |
| **Chunking (청킹)** | 긴 문서를 검색하기 좋은 작은 조각으로 자르는 일입니다 |
| **Contextual Retrieval** | 조각만 떼어놓으면 무슨 얘기인지 모르니, 조각 앞에 짧은 설명을 붙여 색인하는 방법입니다 |
| **Indexing (색인)** | 질문이 들어오기 전에 미리 문서를 찾기 좋은 형태로 정리해두는 작업입니다. 책 뒤의 색인과 같은 개념입니다 |
| **Retrieval (검색)** | 질문이 들어온 다음, 색인에서 관련 자료를 꺼내오는 작업입니다. 색인과는 다른 단계입니다 |
| **BM25** | 글자가 정확히 일치하는 문서를 찾아 점수를 매기는 오래된 검색 방식입니다. 종목코드, 접수번호에 강합니다 |
| **Embedding (임베딩)** | 글의 뜻을 숫자 목록으로 바꾸는 것입니다. 뜻이 비슷하면 숫자도 가까워집니다 |
| **Vector Search** | 임베딩끼리의 거리를 재서 뜻이 가까운 문서를 찾는 검색입니다. 단어가 안 겹쳐도 찾습니다 |
| **Hybrid Search** | BM25와 Vector Search를 같이 돌리고 결과를 합치는 것입니다 |
| **RRF** | 두 검색의 점수 체계가 달라서 그냥 더할 수 없으니, 순위를 기준으로 합치는 방법입니다 |
| **Reranker** | 1차로 찾아온 후보 수십 개를 질문과 다시 하나씩 비교해 정밀하게 줄 세우는 장치입니다 |
| **Agentic RAG** | 검색을 할지 말지, 어떤 도구를 쓸지, 결과가 충분한지, 다시 찾을지를 LLM이 판단하는 구조입니다 |
| **recall@10** | 검색 결과 10개 안에 정답이 들어온 질문의 비율입니다 |
| **hit@1** | 첫 번째 결과가 바로 정답인 질문의 비율입니다 |
| **MRR@10** | 정답이 몇 등으로 나왔는지를 반영한 점수입니다. 1등이면 1점, 3등이면 0.333점 |
| **ablation** | 기능을 하나씩 더하거나 빼면서 성능 변화의 원인을 확인하는 실험 방식입니다 |
| **부트스트랩 신뢰구간** | 같은 실험을 반복하면 결과가 어느 범위에 들어올지 추정한 것입니다. 범위에 0이 들어 있으면 "차이가 있다"고 말하기 어렵습니다 |

## 재현 방법

```bash
# 브랜치: feat/vault-search-indexing

# 지식 레이어 만들고 검증
uv run python scripts/build_knowledge_bundle.py --vault vault

# 평가 질문 생성 (고정 seed 20260824, 항상 같은 636건)
uv run python scripts/eval_retrieval.py gen --vault vault --out eval/queries.json

# 변형별 인덱스 만들기
for v in V0 V1 V2 V3 V4 V5 V6; do
  uv run python scripts/build_search_index.py --variant $v --db data/index_variants/$v.sqlite3
done

# 채점
uv run python scripts/eval_retrieval.py score --queries eval/queries.json --index-dir data/index_variants

# 그냥 검색해보기
uv run python scripts/search_vault.py "삼성전자 반도체 설비투자" --k 5
```

이 문서의 수치는 다음과 같이 얻었습니다.

- **V0에서 V6까지의 표**: 2026-08-25에 인덱스 7개를 다시 만들고 다시 채점했습니다. 질문 유형별 반환량, 짝지은 부트스트랩 신뢰구간 2,000회, 사람 질문의 단어 겹침 비율을 추가로 측정했습니다.
- **V7과 지식 레이어 수치**: 저장소의 `eval/eval_okf_results.json`, `eval/okf_build.json`, `eval/okf_validate.json`을 직접 읽어 확인했습니다.
- **목록표 행 수와 브랜치 상황**: `data/index.sqlite3`와 git을 직접 열어 확인했습니다.
