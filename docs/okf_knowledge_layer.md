# OKF 지식 레이어와 그 위의 검색 — 5주차 실습 기록

4주차까지는 `10_Sources`의 원본 마크다운을 그대로 청킹해 색인했다. 5주차는 그 사이에
**지식 레이어**를 하나 넣는다. 원본은 증거로 그대로 두고, 파생 레이어를 OKF(Open
Knowledge Format) v0.1 규약에 맞춰 `vault/20_Knowledge/`에 만든 뒤, 인덱스가 그 레이어를
소비하게 한다.

```bash
uv run python scripts/build_knowledge_bundle.py --vault vault      # 번들 생성 + 검증
uv run python scripts/build_search_index.py --variant V6           # 대조군: 원본에서 색인
uv run python scripts/eval_retrieval.py score --index-dir data/index_variants
```

---

## 1. OKF를 이 코퍼스에 어떻게 적용했나

OKF 명세가 요구하는 것은 사실상 하나다 — **모든 concept 파일에 `type` 필드**. 나머지
(`title`/`description`/`resource`/`tags`/`timestamp`)는 관례이고, 관계는 일반 마크다운
링크로 표현하며, 디렉터리마다 `index.md`, 번들 루트에 `log.md`를 둔다.

### 무엇을 concept으로 볼 것인가

원본의 `source_type`(수집 경로)을 그대로 타입으로 쓰지 않았다. 지식 레이어의 타입은
'어디서 가져왔나'가 아니라 '무엇에 대한 지식인가'여야 한다.

| concept type | 수 | 무엇인가 |
|---|---:|---|
| `MarketCommentary` | 1,990 | 텔레그램 채널 메시지 |
| `DartFiling` | 1,362 | DART 공시 |
| `Security` | 839 | 13F가 이름만 보고한 보유 종목 (식별자 없음) |
| `BlogPost` | 517 | 네이버 블로그 글 |
| `SecFiling` | 396 | SEC 공시 |
| `Company` | 335 | 종목 (종목코드·티커로 식별) — 관계 허브 |
| `ResearchNote` | 324 | IB·증권사 리서치 |
| `HoldingsSnapshot` | 198 | 13F 보유 현황 스냅샷 |
| `SourceChannel` | 30 | 블로그·채널·IB 하우스 |
| `Investor` | 5 | 13F 보고 주체 |
| `Essay` | 1 | 에세이 |

총 **5,997개 concept**. 문서 concept 4,788건 위에 허브 concept 1,209건이 얹혀 있다.

### status — 원본에 적을 자리가 없던 것들

| status | 수 | 의미 |
|---|---:|---|
| `stable` | 4,238 | 본문이 있고 최신 버전 |
| `stub` | 1,534 | 본문 미확보(링크만). 원본 `content_capture.mode=metadata_only` |
| `corrupt` | 211 | 인코딩이 깨져 본문을 신뢰할 수 없음 |
| `superseded` | 14 | 같은 기준일·유형의 재제출본이 존재 |

`corrupt` 211건은 이번에 처음 드러난 문제다. 옛 DART 공시 일부가
인코딩이 깨진 채 저장돼 있는데(본문 평균 63.3%만 판독 가능,
손상 문자 3,063,124개 = 코퍼스 본문의 11.4%), **원본 스키마에는 그 사실을 적을 자리가 없어**
그대로 색인돼 왔다. 지식 레이어가 생기니 기록할 곳이 생겼다.

### 관계 — 원본에 없던 것을 복원하다

텔레그램·블로그·IB 문서는 frontmatter에 종목 정보가 전혀 없다(`companies: []`).
상장법인 명부를 매칭 사전으로 삼아 본문에서 종목을 찾아 관계로 승격했다: **1,849건**.

1차 시도에서 그중 26.3%가 증권사·운용사 이름이었다 — '분석 대상'이 아니라 '분석 주체'다.
한 덩어리로 두면 "에이피알을 다룬 문서"를 찾을 때 교보증권이 쓴 다른 종목 리포트가 딸려온다.
둘을 다른 관계로 분리했다: 언급 종목 1,849건 / 분석 주체 764건.

### 검증기가 잡아낸 것

OKF의 장점 하나는 관계가 마크다운 링크라서 **기계로 검증된다**는 것이다.

- 1차 빌드: 13F 보유종목 링크 **4,674개가 깨져 있었다**. 관계는 만들었는데 대상 concept 파일을 안 만든 것.
  → `Security` 타입을 도입해 839개 concept을 만들고 해결.
- 현재: 파일 6,010개 · 링크 14,649개 · **깨진 링크 0** · 필수 필드 위반 0 · index.md 없는 디렉터리 0

## 2. 지식 레이어를 인덱스가 소비하게 하기

**OKF 자체는 검색을 개선하지 않는다.** 같은 청킹·같은 토크나이저로 원본에서 색인한 V6와
OKF 번들에서 색인한 V7은 자동 평가셋에서 recall@10이 0.978로 동일하다. 형식일 뿐이기 때문이다.

달라지는 지점은 인덱스가 OKF의 확정 필드를 **필터 컬럼으로** 들여올 때다.

```sql
-- chunk_meta에 추가된 컬럼
okf_type TEXT, entity_key TEXT, period_year TEXT, pub_year TEXT, okf_status TEXT
CREATE INDEX idx_chunk_entity ON chunk_meta(entity_key, period_year);
```
질의에서 엔티티·기간·유형 슬롯을 뽑아 검색 **전에** 후보를 좁힌다.

```
"교보증권이 제시한 에이피알 목표주가"
   → entity=에이피알(kr-278470) · analyst_house=교보증권(필터 아님)
     · type∈{ResearchNote, MarketCommentary}
```

### 실측

**E 계열 — 엔티티+기간+유형으로만 구분되는 질의 (160건)**

같은 회사 공시가 코퍼스에 최대 785건 있고, 그중 하나를 특정해야 한다.

| 구성 | recall@10 | hit@5 | hit@1 | MRR@10 | 지연(중앙값) |
|---|---:|---:|---:|---:|---:|
| V6 — 원본에서 색인 (4주차 최종) | 1.000 | 1.000 | 0.894 | 0.938 | 68.8ms |
| V7 — OKF 번들에서 색인, 필터 없음 | 1.000 | 1.000 | 0.825 | 0.902 | 64.0ms |
| **V7 + 메타데이터 프리필터** | 1.000 | 1.000 | 0.969 | 0.984 | 28.9ms |
| V7 + 프리필터 + 적응 루프 | 1.000 | 1.000 | 0.969 | 0.984 | 29.3ms |

recall은 이미 1.000이라 더 올릴 곳이 없었다. 대신 **1등 정확도가 0.894 → 0.969**로,
**지연시간이 68.8ms → 28.9ms(2.4배)**로 바뀌었다. 후보를 미리 좁히면 BM25가 훑을 게 줄어든다.

**D 계열 — 사람이 원문을 베끼지 않고 쓴 질문 (24건)**

| 구성 | recall@10 | hit@5 | hit@1 | MRR@10 | 지연(중앙값) |
|---|---:|---:|---:|---:|---:|
| V6 — 원본에서 색인 (4주차 최종) | 0.500 | 0.333 | 0.125 | 0.237 | 65.4ms |
| V7 — OKF 번들에서 색인, 필터 없음 | 0.500 | 0.375 | 0.167 | 0.267 | 59.2ms |
| **V7 + 메타데이터 프리필터** | 0.583 | 0.417 | 0.250 | 0.333 | 37.8ms |
| V7 + 프리필터 + 적응 루프 | 0.542 | 0.417 | 0.250 | 0.328 | 45.2ms |

**D 계열 중 어휘 접점이 있는 15건**

| 구성 | recall@10 | hit@5 | hit@1 | MRR@10 | 지연(중앙값) |
|---|---:|---:|---:|---:|---:|
| V6 — 원본에서 색인 (4주차 최종) | 0.800 | 0.533 | 0.200 | 0.379 | 68.4ms |
| V7 — OKF 번들에서 색인, 필터 없음 | 0.800 | 0.600 | 0.267 | 0.427 | 71.3ms |
| **V7 + 메타데이터 프리필터** | 0.867 | 0.667 | 0.400 | 0.526 | 40.3ms |
| V7 + 프리필터 + 적응 루프 | 0.867 | 0.667 | 0.400 | 0.524 | 44.7ms |

4주차에서 역전됐던 지점이다. 청킹·bigram만으로는 V0(문서 단위)의 0.933을 못 따라잡았는데,
지식 레이어의 엔티티·기간 필터가 들어가자 **MRR 0.379 → 0.526(+39%), hit@1 0.200 → 0.400(2배)**로
올라갔다. recall도 0.800 → 0.867.

**자동 생성 평가셋 (636건) — 회귀 확인용**

| 구성 | recall@10 | hit@5 | hit@1 | MRR@10 | 지연(중앙값) |
|---|---:|---:|---:|---:|---:|
| V6 — 원본에서 색인 (4주차 최종) | 0.978 | 0.948 | 0.802 | 0.862 | 28.1ms |
| V7 — OKF 번들에서 색인, 필터 없음 | 0.978 | 0.939 | 0.803 | 0.861 | 28.3ms |
| **V7 + 메타데이터 프리필터** | 0.973 | 0.934 | 0.799 | 0.856 | 29.4ms |
| V7 + 프리필터 + 적응 루프 | 0.973 | 0.934 | 0.799 | 0.856 | 30.3ms |

프리필터가 이 평가셋을 망가뜨리지 않는지 보는 안전장치다. 0.978 → 0.973으로 사실상 무해.

## 3. 슬롯 추출이 틀리면 필터는 정답을 지운다

프리필터를 처음 켰을 때 자동 평가셋 recall이 **0.978 → 0.891**로 떨어졌다. 원인을 세어보니
잃은 55건 중 **50건이 오탐 연도 슬롯**이었다.

```
질의: "신용 2020 선행하는 년까지 2022 수를 충격은 중국 개월"
  → 잘못 걸린 슬롯: year=2020   (정답 문서는 2022년)
질의: "578,563 1,467,036 2025.4 853,151 영업활동현금흐름"
  → 잘못 걸린 슬롯: year=2025   (금액·날짜 숫자를 연도로 오인)
```
`\d{4}`를 연도로 보면 안 된다 — 금액·수량·계좌번호에 4자리 숫자가 널려 있다.
연도 신호(`년`, `FY`, `Q1`)가 명시된 경우에만 슬롯을 만들도록 고치자 0.973으로 회복했다.

이 문제를 두 가지 방법으로 각각 갚아봤다:

| 대응 | 자동 636 recall@10 |
|---|---:|
| 오탐 슬롯 그대로 + 필터 | 0.891 |
| 오탐 슬롯 그대로 + **적응 루프**(커버리지 낮으면 필터 완화) | 0.931 |
| **슬롯 규칙 수정** + 필터 | **0.973** |

루프는 손실의 절반을 갚았지만, 규칙을 고치는 쪽이 압도적으로 낫다.
**에이전트 루프로 덮기 전에 결정론적 규칙을 고치는 것이 먼저다.**

## 4. Contextual Retrieval — 생성형 대신 메타데이터 투영

Anthropic 원안은 문서 전체를 LLM에 넣어 청크별 문맥 문장을 *생성*한다(50~100 토큰).
여기서는 concept의 `description`을 그대로 청크 앞에 붙였다 — 사람이 읽는 요약과
검색용 문맥이 같은 필드다(따로 관리하면 반드시 어긋난다). LLM 비용 0.

문맥 헤더만 켜고 끈 A/B:

| 평가셋 | 문맥 없음 실패율 | 문맥 있음 실패율 | 실패율 감소 |
|---|---:|---:|---:|
| 자동생성 636 | 0.028 | 0.022 | 22.3% |
| E 엔티티기간 160 | 0.000 | 0.000 | 0.0% |
| D 사람 24 | 0.542 | 0.500 | 7.7% |

원안이 보고한 수치는 **top-20 청크 검색 실패율 5.7% → 2.9%(49% 감소, contextual embeddings +
contextual BM25)**, 리랭커까지 얹으면 1.9%(67% 감소)다. 직접 비교는 안 된다 — 원안은 임베딩을
쓰고 코퍼스도 다르다. 다만 방향은 같고, 크기는 훨씬 작다.

작은 이유는 분명하다. 원안이 문맥을 생성해 채워 넣는 정보(무슨 회사, 언제, 어떤 문서)를
이 코퍼스는 수집기가 이미 메타데이터로 갖고 있다. **메타데이터가 없는 코퍼스에서는
이 대체가 성립하지 않는다.** 생성형 경로는 `contextualize.GenerativeContextualizer`로
코드에 있지만 이번 실습에서 실행하지는 않았다(원안 단가 기준 전량 처리 추정 $16).

## 5. 여전히 못 푸는 것

사람이 쓴 24개 질문 중 9개는 질의 토큰의 40% 미만만 정답 문서에 존재한다.

| 질문 | V6 | V7+필터 |
|---|---:|---:|
| 듀케인 패밀리오피스 2014년 6월말 최대 비중 종목은 | 실패 | 10위 |
| 베일리기포드 2025년 4분기 13F 편입 종목 개수 | 실패 | 실패 |
| AI 데이터센터 투자 규모가 얼마나 빠르게 불어나고 있나 | 실패 | 실패 |
| 제이미 다이먼이 바퀴벌레에 비유하며 경고한 계기 | 실패 | 실패 |
| 하워드 막스가 최근 신용 사고를 어떤 전조로 봤나 | 실패 | 실패 |

엔티티·기간이 명시된 한 건(듀케인)만 메타데이터가 건져냈다. 나머지 8건은 어휘가 겹치지
않아 **어떤 어휘 기반 검색으로도 도달할 수 없다.** OKF도 임베딩을 대신하지 못한다.

## 6. 다음 단계

1. **임베딩 + Hybrid Search(RRF).** 위 8건이 정확히 벡터가 필요한 질의다. 이번에 만든
   BM25 인덱스가 하이브리드의 어휘 쪽 절반이 되고, OKF 메타데이터 필터는 양쪽 공통 전처리로 남는다.
2. **Grader를 LLM으로.** 지금 적응 루프의 판정은 어휘 커버리지 대용치다. 의미는 같은데
   표현이 다른 근거를 '관련 없다'고 잘못 버린다 — 이게 루프의 상한이다.
3. **`document_assets` 폐기 또는 OKF 연결.** 티커 필터가 코드에는 있고 데이터가 없어 죽어 있다.
   지식 레이어의 `entities.subject`가 그 자리를 대신할 수 있다.
4. **`stub` 1,534건 본문 확보 · `corrupt` 211건 재수집.** 코퍼스의 1/3이 제목만 있고,
   4.4%는 읽을 수 없다. 검색 품질의 상한을 여기서 깎고 있다.
