# 데이터 Indexing 실험 기록 — 검색 가능한 형태로 저장하기

이 문서는 `investor_intel/indexing/` 패키지를 왜 이렇게 만들었는지, 각 처리가 검색 품질에
실제로 얼마나 기여했는지를 실측치로 남긴 기록이다. 모든 수치는 다음으로 재생성된다.

```bash
uv run python scripts/eval_retrieval.py gen --vault vault --out eval/queries.json
for v in V0 V1 V2 V3 V4 V5 V6; do
  uv run python scripts/build_search_index.py --variant $v --db data/index_variants/$v.sqlite3
done
uv run python scripts/eval_retrieval.py score --queries eval/queries.json --index-dir data/index_variants
```

---

## 1. 출발점 — 지금 저장소는 '검색'을 못 한다

`data/index.sqlite3`의 테이블은 `documents`, `document_assets`, `collector_state`, `dart_corp_codes` 넷이다. `documents` 테이블에는
본문 텍스트 컬럼이 없고 FTS 가상 테이블도 없다. 조회 함수도 `find_duplicate`,
`has_transcript_for_period`, `latest_filing_for_ticker`처럼 **중복 제거와 수집 상태 추적**용이지
내용 검색용이 아니다. 즉 이 인덱스는 카탈로그이지 검색 인덱스가 아니다.

실측으로 확인한 문제 네 가지:

| 문제 | 실측 |
|---|---|
| `document_assets`가 완전히 비어 있음 | 행 0개. frontmatter `assets`가 4,818건 중 0건 채워짐. 이 테이블을 JOIN하는 `latest_filing_for_ticker()`는 NBIS/BE/RDDT 어느 티커로도 항상 `None`을 반환한다 (같은 티커의 SEC 공시는 각각 242/132/22건 존재) |
| 인덱스가 vault보다 뒤처짐 | `documents` 4,370행 vs vault 원문 4,818건 — 448건 누락 |
| 문서 길이가 극단적으로 치우침 | 중앙값 813자인데 p95 40,592자, 최대 1,476,399자. 8,000자 초과 문서는 631건(13%)뿐이지만 **전체 글자수의 82%**를 차지한다 |
| 본문이 아예 없는 문서가 1/3 | `content_capture.mode=metadata_only` 1,552건 (32%). DART 1,059건, SEC 355건 |

부수적으로: 모든 문서에 동일한 수집기 안내문이 붙어 있고(전체 글자수의 4.2%), `## 핵심 주장`,
`## 근거`, `## 반대 근거`, `## 포트폴리오 관련성` 네 섹션은 4,818건 **전부** 비어 있다
(`llm_processed=True`인 문서 0건 — analyze 단계가 이 데이터에는 아직 돌지 않았다).
또 서로 다른 경로에 같은 `id`를 가진 사본이 30쌍 있다(재수집 시 `published_at`이 바뀌면
`path_for_document`가 새 파일을 만들기 때문).

## 2. 파이프라인 — Load / Split / Contextualize / Store

```
vault/10_Sources/**/*.md
   │  loader.py        frontmatter 파싱 · 보일러플레이트 제거 · 중복 id 스킵 · 본문 유무 판정
   ▼
LoadedDocument
   │  splitter.py      섹션 → 표/문단 블록 → (상한 초과 시) 문장 경계 분할, 표는 헤더 반복
   ▼
Chunk[]
   │  splitter.context_header()   출처·종목·공시유형·기준일·제목·섹션을 청크 앞에 결정론적으로 부착
   ▼
(ctx, title, body) 3컬럼
   │  tokenizer.py     한글 문자 bigram + 어절 원형 + 식별자 분해
   ▼
bm25_index.py         SQLite FTS5(BM25). 컬럼 가중치로 메타데이터 부스팅, 검색 시 문서 단위 집계
```

### 설계상 밝혀둘 점

- **Contextual Retrieval을 LLM 없이 구현했다.** Anthropic 원안은 문서 전체를 LLM에 넣어 청크별
  설명을 *생성*한다. 여기서는 frontmatter와 섹션 경로를 투영할 뿐이다. 이 코퍼스는 수집기가
  이미 구조화된 메타데이터를 붙여두기 때문에 생성형이 만들 정보의 상당 부분이 확정값으로
  존재한다. 대신 '이 청크가 문서의 논지에서 어떤 역할인가' 같은 문맥은 얻지 못한다. 비용 0의 대가다.
- **형태소 분석기를 쓰지 않았다.** mecab/khaiii가 더 정확하지만 사전·설치 의존성이 생긴다.
  문자 bigram은 재현율을 크게 올리는 대신 걸친 조각('전자의')도 만들어 정밀도를 일부 희생한다.
- **임베딩이 없다.** 이번 실험은 어휘 기반 검색만 다룬다. 이 선택의 대가는 4절에 정면으로 나온다.

## 3. Ablation — 무엇이 실제로 기여했나

자동 생성 평가셋 636건 (A1 구절_원형 193 / A2 구절_기본형 193 / B 한국어_형태변형 100 / C 식별자 150).
정답은 문서 id로 정의해 문서 단위 인덱스와 청크 단위 인덱스를 공정하게 비교한다.

| 변형 | 추가한 처리 | recall@10 | MRR@10 | hit@1 | top-5 반환 글자수(중앙값) |
|---|---|---:|---:|---:|---:|
| V0 | 현행 수준 — 문서 단위 · 어절 토큰 | 0.810 | 0.704 | 0.640 | 20,200 |
| V1 | + 구조 인식 청킹 | 0.822 | 0.743 | 0.698 | 2,789 |
| V2 | + 한글 bigram 토크나이징 | 0.969 | 0.848 | 0.788 | 2,922 |
| V3 | + 문맥 헤더 · 보일러플레이트 제거 | 0.969 | 0.870 | 0.818 | 2,983 |
| V4 | + 메타데이터 가중 · 본문없음 분리 | 0.821 | 0.716 | 0.663 | 3,056 |
| V5 | + 메타데이터 가중만 (본문없음 유지) | 0.973 | 0.868 | 0.816 | 2,961 |
| V6 | + 어절 원형 토큰 병기 (권장) | 0.972 | 0.859 | 0.802 | 2,899 |
| **최종** | V6 + 문서집계(max) — 최종 | 0.978 | 0.862 | 0.802 | 2,937 |

부트스트랩(2,000회 재표본) 95% 신뢰구간으로 본 단계별 기여:

| 단계 | Δrecall@10 | 95% CI | 판정 |
|---|---:|---|---|
| V0 → V1 구조 인식 청킹 | +0.013 | [+0.000, +0.027] | 유의하지 않음 |
| V1 → V2 한글 bigram | **+0.146** | [+0.119, +0.176] | **유의** |
| V2 → V3 문맥 헤더·보일러플레이트 제거 | +0.000 | [−0.009, +0.009] | 유의하지 않음 |
| V3 → V5 메타데이터 가중 | +0.005 | [+0.000, +0.011] | 유의하지 않음 |
| V5 → V6 어절 원형 병기 | −0.002 | [−0.008, +0.005] | 유의하지 않음 |
| V0 → V6 전체 | **+0.162** | [+0.134, +0.193] | **유의** |

### 읽는 법

**recall 개선의 거의 전부는 한국어 토크나이징에서 나왔다.** 나머지 처리는 이 평가셋에서
통계적으로 유의한 recall 차이를 만들지 못했다. 특히 B 계열(한글 형태 변형)에서
V0·V1은 **recall 0.000** — 어절 단위 색인은 '삼성전자의'로 저장된 문서를 '삼성전자'로
찾는 것이 원리적으로 불가능하다. V2에서 0.930으로 뛴다.

**청킹의 값어치는 recall이 아니라 컨텍스트 비용이다.** recall은 거의 그대로인데 top-5 반환
글자수가 20,200자 → 2,789자로 7.2배 줄었다. A 계열만 보면 52,093자 → 3,252자로 16배다.
문서 단위 인덱스는 '정답을 찾긴 하는데 건초더미째 돌려주는' 상태였다.

**V4는 실패한 실험이다.** `metadata_only` 문서를 검색에서 통째로 제외했더니 C 식별자 계열
recall이 1.000 → 0.340으로 무너졌다. accession number로 찾는 공시가 대부분 본문 없는
문서이기 때문이다. 원인을 분리하려고 만든 V5(메타데이터 가중만)는 0.987을 유지한다.
*전처리로 무언가를 버릴 때는 그 데이터가 어떤 질의 유형의 유일한 정답인지 먼저 확인해야 한다.*

## 4. 자동 평가셋이 숨긴 것 — 사람이 쓴 질문으로 다시 재기

자동 질의는 정답 구절에서 단어를 뽑아 만들기 때문에 어휘가 겹친다. 실제 사용자는 그렇게
검색하지 않는다. 그래서 실제 문서 12건을 읽고 '문서를 안 읽은 사람이 쓸 법한' 질문 24개를
따로 라벨링했다(원문 표현을 그대로 베끼지 않는 것을 규칙으로 삼음).

| 평가셋 | Before recall@10 | After recall@10 | Before MRR | After MRR | Before ctx5 | After ctx5 |
|---|---:|---:|---:|---:|---:|---:|
| 자동 636건 | 0.810 | 0.978 | 0.704 | 0.862 | 20,200 | 2,937 |
| 사람이 쓴 질문 24건 | 0.583 | 0.500 | 0.264 | 0.237 | 12,913 | 2,525 |
| └ 어휘 접점 있는 15건 | 0.933 | 0.800 | 0.422 | 0.379 | 17,401 | 2,422 |
| └ 어휘 불일치 9건 | 0.000 | 0.000 | 0.000 | 0.000 | 12,065 | 2,588 |

### 결과가 뒤집힌다

사람이 쓴 질문에서는 **After가 Before보다 낮다** (0.500 vs 0.583). 두 가지가 겹쳤다.

1. **어휘 불일치 — 이건 어떤 변형도 못 푼다.** 24건 중 9건은 질의 토큰의 40% 미만만 정답
   문서에 존재한다. "제이미 다이먼이 바퀴벌레에 비유하며 경고한 계기", "하워드 막스가 최근
   신용 사고를 어떤 전조로 봤나" 두 건은 겹치는 토큰이 **0개**다. 이 9건은 V0~V6 전부 recall
   0.000이다. 어휘 기반 검색의 천장이고, 임베딩 없이는 넘을 수 없다.
2. **어휘 접점이 있는 15건에서도 Before가 앞선다** (0.933 vs 0.800). 문서 단위 색인은 흩어진
   질의어가 한 문서 안에서 자연히 합산되는데, 청크로 자르면 그 합산이 사라진다. 다만 정답
   문서 안에서 매칭 토큰의 96%(중앙값)가 단일 청크에 모여 있으므로, 근거가 쪼개진 탓은
   아니다 — 청크 수가 4,788 → 47,121로 늘어 경쟁자가 10배가 된 탓이다.

2번에 대한 대응이 `search_documents()`(문서 단위 집계)다. 상위 청크를 문서로 묶고 문서당
최고 청크 점수로 순위를 매긴다. 실측:

| 집계 방식 | 자동 636건 recall | 사람 24건 recall | 사람 24건 MRR |
|---|---:|---:|---:|
| 집계 없음 (청크 반환) | 0.972 | 0.458 | 0.226 |
| **문서집계 max (기본값)** | **0.978** | **0.500** | 0.237 |
| 문서집계 top2 점수합 | 0.936 | 0.417 | 0.245 |
| 문서집계 top3 점수합 | 0.885 | 0.458 | 0.277 |

점수를 합산하면 '약한 매칭이 여러 개인 긴 문서'가 '강한 매칭 하나인 짧은 문서'를 이겨서
자동셋 recall이 무너진다. 그래서 기본값은 max다. 이래도 Before의 0.583에는 못 미친다.

주의: 24건(하위 집합 15건)은 표본이 작다. 이 역전은 방향을 보여주는 신호로 읽어야 하며,
정밀한 효과 크기로 읽으면 안 된다.

## 5. 결론과 다음 단계

**확정된 것**

1. 한국어 코퍼스에서 어절 단위 색인은 형태 변형 질의를 원리적으로 못 찾는다. bigram 색인이
   유일하게 통계적으로 유의한 개선을 만들었다 (+14.6%p, CI [+11.9, +17.6]).
2. 청킹의 값어치는 정확도가 아니라 컨텍스트 비용이다 (top-5 기준 7.2배, 긴 문서만 보면 16배).
3. 전처리로 데이터를 버리는 결정은 질의 유형별로 검증해야 한다 (V4의 −66%p).
4. 어휘 기반 검색만으로는 패러프레이즈 질문의 37.5%가 원리적으로 도달 불가다.

**다음 단계 (우선순위 순)**

1. **임베딩 추가 후 Hybrid Search + RRF.** 4절의 9건이 정확히 벡터 검색이 필요한 질의다.
   다국어 모델(한국어 3,977건 / 영어 841건)이어야 한다.
2. **`document_assets` 채우기.** 티커 필터는 코드가 이미 있는데 데이터가 없어 죽어 있다.
   `companies` frontmatter(42.8% 채워짐)를 `assets`로 승격하는 것이 가장 싼 수리다.
3. **`metadata_only` 1,552건의 본문 확보.** 코퍼스의 1/3이 제목만 있는 상태로
   색인돼 있다. 검색 품질의 상한을 여기서 깎고 있다.
4. **평가셋 확대.** 사람이 쓴 질문 24건은 너무 적다. 최소 100건, 질의 유형별 층화 필요.
